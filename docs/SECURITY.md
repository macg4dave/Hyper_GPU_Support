# Security and recovery

This page owns product authority/trust boundaries and recovery semantics. [AGENTS.md](../AGENTS.md) owns agent authorization rules; [testing](ENGINEERING.md#validation-and-live-acceptance) owns qualification scenarios. These are contracts to preserve and validate, not a claim that static review proves their enforcement.

## Authority and trust

- Protected enrollment binds the initiating operator, exact existing VM GUIDs/GPU interfaces, and installed artifact identities. Runtime intent, observed attachment, or a GUI draft cannot grant that authority.
- Routine artifact reinstall preserves the existing operator and exact pair identities under the common lock before changing existing permissions or task availability. It rejects authority replacement; a durable package-bound receipt preserves interrupted policy/pending-pair publication and archives readback before releasing installation admission.
- Additive enrollment reviews the current policy revision and operator, appends one pair, and preserves others. GPU replacement is a distinct unavailable transition. Initial setup reviews a fixed four-artifact package and keeps package inputs locked across elevation.
- Elevated setup and worker entrypoints accept fixed typed operations, validated session identities, and authenticated peer processes. Preserve operator SID checks, process binding, local pipe restrictions, frame/output limits, and deadlines. Do not substitute an owner-SID check for exact launched-process authentication.
- Privileged directories/files require trusted ownership, restrictive permissions, and reparse/path checks. Fixed destinations come from Windows known folders. A configuration import or save cannot name an arbitrary privileged destination.
- Installed artifacts are hash-bound to enrollment. Driver payload trust uses Windows signatures/catalog membership and per-file integrity; the mere presence of a catalog is insufficient.
- Effects revalidate fresh enrollment, target identity, provider limits, power, conflicts, driver/payload identity, and the reviewed plan under the protected operation lock. Never execute an old approved plan merely because its displayed summary has not changed.

The relevant implementations are [runner](../src/worker/runner/mod.rs), [worker](../src/worker/mod.rs), [setup](../src/setup.rs), [session pipes](../src/windows_pipe/session.rs), [security](../src/security.rs), and [trust](../src/trust.rs). APP-007 audits concrete trust/recovery gaps in the agreed workflow; APP-008 validates meaningful failure coverage.

## Guest OS eligibility before installation

Windows-version checking is deferred. GPU installation, driver refresh and Repair / Reinstall do not query version/build/edition, maintain a release allowlist or refuse a guest because of its Windows version. Setup displays a non-blocking compatibility warning. Existing Hyper-V OS labels and display caches remain presentation-only; VM names are never installation authority. This does not claim that every Windows version is supported.

The normal authenticated PowerShell Direct transport, local credentials, signed payload and artifact validation, protected admission, guest preparation and independent graphics checks still apply. Transport or preparation failures must identify the actual failing component and retain recovery when effects are uncertain. A malformed reply does not establish OS incompatibility. Installation never mounts or unlocks disks, requests BitLocker keys, changes encryption settings or force-stops a guest. An unavailable guest session remains an actionable communication failure.

The [workflow](../src/workflow/apply.rs) journals actual preparation and VM power transitions. No extra boot/shutdown is performed for version identification. Known legacy compatibility failure envelopes and plan action values remain readable for existing recovery evidence; new plans never emit an OS-check action. Source regression coverage includes setup, driver refresh and reinstall from Running/Off with a failing version hook, plus execution of the fixed transport with isolated guest entrypoints. Live VM/guest acceptance is separate from the non-hardware gate.

## Prepared payload lifetime

OPT-004 prepares Apply/Verify in the exact elevated process that executes it. The fixed process-bound pipe, authenticated operator, installed artifacts and common lock remain mandatory. The first request binds the exact VM/GPU, action/reinstall intent and expected configuration revision. Preparation performs no guest access, journal/effect writes or credential acquisition. Its fresh authenticated plan includes payload, operational facts, permitted actions, lifecycle and credential requirements. The worker retains the native backend/manifest and a consumed, non-serializable admission token; no frontend-supplied digest can construct that token.

The client checks the returned operation identity and current GUI draft/selection/revision, then obtains credentials locally where the prepared scope requires them. Approval echoes a hash of the entire prepared review, session identity and shutdown approval. Unknown/repeated/mismatched approval or missing/unexpected credentials fails before effects. The exact review revision is written into the existing audit binding before acknowledgement. Saved revision, recovery/provider holds and current operational facts are checked again before execution. Eligible ordinary CLI predictions retain their existing full admission comparison and cannot expand into guest/setup work on payload drift; missing/adverse history instead enters full worker preparation. Explicit CLI plans remain read-only full authentication.

All admitted payload sources, including catalogs, are opened before hashing and held without write/delete sharing through execution and independent final authentication. Conflicting writers cause refusal. Fresh pre-effect discovery rechecks driver identity and expanded file/catalog membership against the retained manifest without another complete hash pass. Source byte replacement cannot be authorized by a matching version string. Signature/catalog membership and guest transfer/launch integrity checks remain in place; an independent complete final pass still precedes `Verified` and publication. No persistent digest cache or reusable attestation is introduced.

Read-only preparation has bounded transport/provider/hash waits and can be abandoned before approval. The connection closes on cancellation/disconnect; admission is retained until the exact launched process exits. Native blocking work can outlast cooperative cancellation, and the existing watchdog remains the hard bound. After approval, effects are never cancelled/replayed by read controls. Effect receipts precede power/installation/mutations, final authentication failure retains recovery, and verified-unsaved results keep the exact save-only contract. A terminal `Complete` reply and process-release observation do not establish a client/guest cleanup acknowledgement; unresolved evidence is ineligible for later retention work. Compilation, regressions, the integrated non-hardware gate and protected installation passed at the [17 October checkpoint](ENGINEERING.md#optimization-validation-checkpoint); installed GUI and VM/GPU/guest qualification remain pending.

## Protected read admission

For a new pair in an installed product, permission preparation uses the current protected observation's authority revision as a proposal token. It does not rehash installed artifacts twice before requesting UAC. The privileged enrollment worker still authenticates its current artifacts/operator/policy, checks the exact target and expected revision, and rejects stale or held proposals before authority writes. First installation retains source-artifact preparation. Local progress/technical details are available before worker events and do not constitute authenticated receipts. A foreground request waits at most 30 seconds for a preceding poll to release before reporting a blocked read; this timeout never retires the poll, starts UAC/effects, or clears recovery. Once release is confirmed, the normal request may be made again.

Installed read requests authenticate the enrolled operator over the local fixed pipe, retain replay protection/audit, acquire the common operation lock and freshly authenticate the complete current artifact policy once under that lock. A changed enrollment snapshot fails closed. No persistent file digest or reusable execution attestation is introduced. Observation/plan readiness is derived from the same authenticated request and never substitutes for independent worker admission or grants effect authority.

Read-only cancellation/deadlines propagate through provider enumeration/object waits, file hashing and pipe waits. The client retains the exact scheduled runner instance returned by launch; closing a pipe, receiving a result or requesting cancellation alone does not release GUI admission. Release requires that instance's terminal scheduler readback: Ready or the explicit `SCHED_E_TASK_NOT_RUNNING` result when the completed one-shot instance is no longer present. Running/Queued continue waiting; Unknown/Disabled, disconnection and other observation errors retain admission. A registered task's transient Ready state is not substituted for exact instance readback. Failed launch/release observation retains admission with an unconfirmed result and safe native diagnostic codes; there is no automatic replay. The server observes client disconnect, cooperatively ends reads and retains its existing hard process watchdog for blocked native calls. Native blocking work can outlast a cooperative deadline; foreground work waits for confirmed release. No task-stop or effect-cancellation mechanism is added.

Operational comparisons exclude optional display metadata only. Required identity, driver, capabilities, assignment/settings, payload, journal, configuration revision and recovery checks retain their fail-closed boundaries. Completion observations are revision-bearing presentation/readback data; they do not clear holds, publish configuration, establish guest health or authorize another operation. Missing selected facts and disappearing expected save receipts remain failures. Implementation is complete in source under OPT-002; the non-hardware gate and installed/live qualification are pending.

Apply plans now carry the reviewed GPU observation, including driver/capabilities, so the worker compares its operational facts independently of optional display metadata. Older serialized plans without that observation cannot be admitted; obtain a fresh plan with the matching candidate binaries. No persistent recovery record is migrated by this plan-contract change.

## Credentials and diagnostics

Credentials are obtained locally, retained only through explicit Windows Credential Manager opt-in, and kept out of desired configuration, journals, audits, public reports, and persistent recovery. Before the prompt, name the selected VM and clearly explain that its Windows credentials are needed, not the host computer's credentials. A credentials settings action does not establish guest connectivity or graphics health. Credential deletion does not revoke pairing.

The shared native prompt path requires acknowledgement of a named-VM explanation before collecting input. Acknowledgement does not authorize remembering; the native Remember checkbox starts unchecked. Cancelling either panel returns before worker submission, so it starts no guest work and does not clear an existing recovery hold. Vault errors remain failures rather than silently falling back to a prompt. Existing explicit opt-in entries may be reused by ordinary operations without prompting. Settings instead always offers a VM/GUID-named replace/forget/cancel choice. Replacement opens fresh native input; checking Remember saves the replacement, while successful input without Remember removes the old entry as disclosed. Cancelling retains the previous entry. Forget is per-user/per-VM and absence is idempotent. These settings perform no guest, power, enrollment or GPU work. Source implementation is complete under APP-005; runtime acceptance remains pending.

Treat adapter error text as untrusted and potentially secret-bearing. Public outcomes use bounded application-owned failure context. Preserve component/stage/numeric-code evidence where safe rather than copy arbitrary stderr into UI/audit output. Diagnostic tracing is opt-in through trusted fixed product paths and runs only in elevated processes; ordinary frontends skip trace-file creation so read-only artifact checks do not require protected write access. Local qualification records must exclude secrets.

## Operation recovery

The [store records](../src/configuration_store.rs) distinguish effect recovery from configuration publication.

VM-bound operation and native-provider holds block only their recorded VM. New operations retain a separate protected receipt for each VM under the existing host operation lock; they do not overwrite, replay or retire another VM's evidence. Reconciliation and save-only resolve the exact original operation ID and retire only its bound receipt after durable terminal audit. Legacy singleton receipts are scoped by their validated VM identity and move only through audited copy/readback/marker publication before an admitted VM operation; interrupted migration retains the original until the identical copy is confirmed. A protected version marker makes older singleton readers fail closed while per-VM receipts exist. Unreadable, inconsistent, duplicate or unknown-scope records remain global blockers, as do unfinished shared authority/configuration imports. Profile deletion is a separately confirmed exception for the selected VM's app records: it binds their complete revision snapshot and discards their recovery records, while preserving unrelated profiles and receipts. The storage/admission correction is implemented in source. Validation: **Passed (complete non-hardware gate)** on 16 October 2026, with 390 product tests, 12 catalogue tests, copy/docs/format checks, strict Clippy, binary builds and API documentation. Evidence: `local/evidence/m1-gate-20261016T095622924Z/`. The six native XML/COM metadata tests and their fixtures were deleted at the user's request; runtime metadata handling is unchanged, and this gate used no test exclusion. Product installation and live multi-VM acceptance remain pending.


| Phase | Meaning | Permitted response |
|---|---|---|
| `Admitted` | Bound operation persisted before effects | Establish current facts independently; do not assume it is safe to replay |
| `EffectsStarted` | Effects may have occurred; terminal outcome not established | Explicit reconciliation from fresh host/guest/recovery evidence; partial/mismatched state remains blocked |
| `Verified` | Independently verified outcome recorded | Retry only the bound save, after checking state/revision/driver/payload consistency |
| `Published` | Bound configuration publication recorded | Confirm the completed publication and safely retire the record |


**Delete profile** is an explicitly selected app-record deletion, available during recovery and independently of VM power or current GPU attachment. Its fresh review binds the enrolled operator and exact VM/GPU pair, all saved-profile/history revisions, and the selected profile's fixed-name operation/provider recovery files. Selecting Delete profile explicitly discards that profile's saved settings, pairing, managed history and interrupted-operation records; it does not establish the interrupted operation's outcome. No VM inspection, power change, GPU detachment, driver removal or guest access is dispatched by deletion. Other profiles and unrelated recovery files are retained. Legacy singleton receipts are deleted only when their contents bind this exact VM. An interrupted batch import loses only this profile's document, so resuming it cannot recreate the deleted profile; other imported documents and their progress remain intact. Unknown/shared records without this profile binding are left alone. The common worker lock, mandatory audit, protected file checks, durable deletion progress and revision/readback checks remain in force. Interrupted deletion resumes only its recorded scope and refuses changed/recreated files. Another unfinished enrollment/deletion cannot be overwritten by a fresh request. Ordinary GPU effects still require enrollment and fresh review after a profile has been deleted.

The separate host-restoration **Remove partial GPU setup** worker disposition retains its exact VM/GPU/journal and shutdown checks. It is not the profile-deletion action offered in the interrupted-operation dialog.

An `Admitted` attempt has no dispatched guest/Hyper-V effects. The explicit foreground recovery action directly checks its recorded outcome, without guest credentials or power changes. **Delete profile** remains a distinct explicitly selected app-record action. The worker independently checks recorded host state/configuration before ending recovery; drift retains the hold. Recovery that actually requires guest/power work includes those transitions under the foreground action and displays the expected final power on progress. There are no separate GUI review dialogs or power-consent checkboxes. Fresh plan/revision/identity binding, Windows prompts and protected worker checks remain mandatory. Refresh, polling and result publication never automatically enter recovery or replay Apply. Native provider admission/administrator reconciliation remains a separate domain with its original evidence requirements. These UI changes do not authorize live effects during source/build validation.

Native provider admission is separate from workflow outcome. New markers capture VM/GPU, exact stage, before facts and requested effect, workflow/configuration tokens, existing job identities and a typed COM failure where available. A missing job reference or unreadable/expired job never permits automatic marker removal. From an administrator console, correlate a surviving local terminal job with the original invocation, then run `hyper-gpu-support native-review --job 'Msvm_ConcreteJob.InstanceID="JOB-ID"'`. The supported review validates the job's affected VM, provider job type, new identity, terminal result, compatible before/after host facts and quiescent job inventory. Inspect its original/fresh facts and returned token before separately approving `hyper-gpu-support native-reconcile --review TOKEN`.

The confirmation uses protected captured terminal evidence if that job has since expired; provider access errors do not count as absence. It rechecks workflow/configuration bindings and exact fresh readback, archives the original marker and terminal result, and retires only provider admission. It does not certify workflow success, save desired intent or replay effects. Without sufficient independent completion evidence (including legacy records lacking scope), preserve the native marker, workflow records and Hyper-V event logs for administrator/provider support. Never manufacture a terminal receipt, delete an uncertain marker or infer completion from instantaneous matching state. Hyper-V job-type/terminal metadata follows the [Microsoft provider contract](https://learn.microsoft.com/en-us/windows/win32/hyperv_v2/msvm-concretejob).


## Qualification limits

Historical incident notes do not establish a current host-lockup cause or permanent fix. This reset imports no old milestone completion or active hold. Future live work needs its own scoped authorization and evidence. Automated IPC/fault tests validate selected software boundaries; they do not establish host stability or concurrent GPU sharing.

## Completed record retention

Retention runs only under the common protected operation lock and never substitutes for admission or terminal auditing. A protected `audit-retention.json` checkpoint limits audit maintenance attempts to once per minute; malformed/future checkpoints preserve records, and read cancellation/deadline checks also bound maintenance. Only strict schema-1, filename/nonce-matched, successful Discover/Observe/Poll/Completion/Status audits are eligible. Keep the newest 32 and everything younger than ten minutes; among the rest, remove oldest records until at most 512 eligible records and 4 MiB remain, and remove eligible records older than seven days. These are bounds on eligible completed read records, not a promise to bound recovery evidence. Started/Failed, effect/plan audits, malformed or unknown records, and files with an adjacent `.retain` marker are preserved. Any active or ambiguous recovery/pending/provider/installation reference suspends the pass. Unsafe paths, links, oversized scans or uncertain metadata suspend cleanup. Recheck exact bytes and protected identity before each removal; deletion failure stops the pass without changing the operation result. No admission/nonce replay protection is removed by audit retention.

Guest staging has no age-based deletion. Each new bundle has a unique identity containing operation, VM, manifest digest, mode and file count, with a random bundle suffix. A protected host descriptor is published before transfer. Only after successful terminal auditing and retirement of that exact operation's recovery receipt may the host durably mark that descriptor completed. A terminal pipe reply or process exit alone cannot mark it completed. Failure or interruption before acknowledgement leaves the bundle ineligible indefinitely; legacy digest-only bundles are retained.

At most two completed descriptors per invocation are delivered only during a later already-authorized preparation/Verify session for that exact VM, after compatibility admission where applicable. Cleanup never starts a VM, obtains credentials or creates a guest session of its own. The guest takes its existing preparation lock and requires an exact descriptor match with the bundle's protected identity before deleting only enumerated staging leaves. Installed payloads, `prepared.json`, helpers, diagnostics and other bundles are outside this namespace. All leaves are validated before deletion; unknown entries, links, duplicate acknowledgements or mismatched identities refuse cleanup. Identity metadata is deleted last so interrupted leaf deletion can resume; an empty directory after identity deletion is also resumable. Cleanup failures retain the host acknowledgement for another authorized session and never change the terminal GPU/guest result. Host acknowledgements retire only after an exact guest cleanup reply, so lost replies are safe to repeat. Administrator `.retain` markers preserve host descriptors and guest bundles. No source-only validation removes operational records.
