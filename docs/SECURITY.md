# Security and recovery

This page owns product authority/trust boundaries and recovery semantics. [AGENTS.md](../AGENTS.md) owns agent authorization rules; [testing](ENGINEERING.md#validation-and-live-acceptance) owns qualification scenarios. These are contracts to preserve and validate, not a claim that static review proves their enforcement.

## Authority and trust

- Protected enrollment binds the initiating operator, exact existing VM GUIDs/GPU interfaces, and installed artifact identities. Runtime intent, observed attachment, or a GUI draft cannot grant that authority.
- Routine artifact reinstall preserves the existing operator and exact pair identities under the common lock before changing existing permissions or task availability. It rejects authority replacement; a durable package-bound receipt preserves interrupted policy/pending-pair publication and archives readback before releasing installation admission.
- Additive enrollment reviews the current policy revision and operator, appends one pair, and preserves others. GPU replacement is a distinct unavailable transition. Initial setup reviews a fixed four-artifact package and keeps package inputs locked across elevation.
- Elevated setup and worker entrypoints accept fixed typed operations, validated session identities, and authenticated peer processes. Preserve operator SID checks, process binding, local pipe restrictions, frame/output limits, and deadlines. Do not substitute an owner-SID check for exact launched-process authentication.
- Privileged directories/files require trusted ownership, restrictive permissions, and reparse/path checks. Fixed destinations come from Windows known folders. A configuration import or save cannot name an arbitrary privileged destination.
- Installed artifacts are hash-bound to enrollment. Driver payload trust uses Windows signatures/catalog membership and per-file integrity; the mere presence of a catalog is insufficient.
- Effects revalidate fresh enrollment, target identity, provider limits, power, conflicts, driver/payload identity, and the reviewed plan under the protected operation lock. Never execute an old approved plan merely because its displayed summary has not changed.

The relevant implementations are [runner](../src/worker/runner/mod.rs), [worker](../src/worker.rs), [setup](../src/setup.rs), [session pipes](../src/windows_pipe/session.rs), [security](../src/security.rs), and [trust](../src/trust.rs). APP-007 audits concrete trust/recovery gaps in the agreed workflow; APP-008 validates meaningful failure coverage.

## Guest OS eligibility before installation

Only identified Windows 11 client releases may receive GPU support. An installation-intent preflight runs during first-setup or explicit Repair / Reinstall review **before driver payload discovery/authentication**. An ordinary driver refresh runs preflight once a changed payload establishes installation intent; unchanged-payload management skips it. Apply repeats the host-only preflight **before reading the credential vault or displaying a guest credential prompt**, and the shared execution path retains its fresh pre-effect check. Startup, discovery, routine refresh, allocation-only changes, disable and verification-only operations do not query compatibility. Optional UI OS icons and labels never authorise installation.

The preflight uses read-only offline inspection for stopped VMs and freshly queried intrinsic Hyper-V metadata as its fallback; a running VM uses host-readable metadata without opening a guest session. It never requests guest credentials, boots a VM or unlocks a volume. If these sources cannot establish Windows 11, preflight blocks before payload authentication or credential access rather than asking for credentials to identify the OS. A subsequent authenticated guest query remains a final installation defence. The narrowly scoped `InstallationOs` protected read operation requires an enrolled enabled target and rejects supplied credentials.

For a stopped VM, the selected current realised VHD is temporarily attached **read-only, without drive letters**, using a handle-bound lifetime. A process-private read-only SOFTWARE hive supplies numeric Windows version/build and `InstallationType=Client`; product-name strings are not used by this primary method. The conservative offline adapter requires a single virtual hard disk, one GPT Windows data partition and one EFI partition, with only recognised reserved/recovery partitions alongside them. Multiple disks, unknown partitions, attached bootable optical media, inaccessible volumes/hives and registry recovery requiring writes leave primary inspection unavailable and may use the metadata fallback below. Observed VM power/disk changes during inspection block admission. No disk contents, BitLocker protectors or guest power are changed for detection. The private hive and temporary disk surface are released before normal installation can boot the guest.

For an **already running** VM, an authenticated PowerShell Direct session reads current `Win32_OperatingSystem` version/build and workstation type, corroborated by the client installation type. This works independently of host-side disk decryption. This query returns before guest bootstrap, transfer or worker launch; it never starts a VM. Before preparation writes, the bridge checks again in its actual session, and the guest worker independently enforces the same release policy. These checks exclude Server and Windows PE even when they share a build number.

When primary inspection cannot identify the OS, the installation boundary freshly queries `Msvm_KvpExchangeComponent.GuestIntrinsicExchangeItems` for the exact VM GUID as the user-requested fallback. This can allow an encrypted stopped VM to proceed without unlocking its disk. Windows approval requires OSName, OSVersion, OSBuildNumber and numeric ProductType; version and build must agree and identify an explicitly supported Windows 11 workstation release. Optional major/minor/platform fields must also agree. A Windows client ProductName may still say Windows 10; the numeric release policy distinguishes Windows 11. Clear Linux/Debian/Ubuntu/FreeBSD or Windows Server OSName reports establish an unsupported OS without requiring Windows-only fields; missing or ambiguous OS evidence remains unidentified. Missing, malformed, duplicate or contradictory approval fields block installation. A positive unsupported primary result or an observed binding change cannot be overridden. UI caches, custom guest/host KVP and VM display names are never consulted for admission.

Intrinsic KVP reports can be historical: querying them now does not guarantee the report describes the current attached disk. The fallback deliberately accepts that limitation at initial admission. Current running OS checks in the preparation session and guest worker remain mandatory before installation writes, so stale metadata cannot override a later unsupported or unidentified running OS. If both primary inspection and usable fallback metadata are unavailable, installation remains blocked. The application never unlocks BitLocker or requests recovery keys, and never boots a VM solely for detection. Firmware/security settings, historical receipts and the presence of encryption are not compatibility evidence.

The supported release/build policy is centralised in [guest compatibility](../src/guest_compatibility.rs), rather than accepting every future build above a threshold. Unknown/new releases are denied until explicitly added. The [offline adapter](../src/windows_hyperv/installation_os.rs) and [guest transport](../src/guest.rs) supply facts; failures cross the worker boundary as fixed typed compatibility reasons, without guest strings or paths.

## Credentials and diagnostics

Credentials are obtained locally, retained only through explicit Windows Credential Manager opt-in, and kept out of desired configuration, journals, audits, public reports, and persistent recovery. Before the prompt, name the selected VM and clearly explain that its Windows credentials are needed, not the host computer's credentials. A credentials settings action does not establish guest connectivity or graphics health. Credential deletion does not revoke pairing.

The shared native prompt path requires acknowledgement of a named-VM explanation before collecting input. Acknowledgement does not authorize remembering; the native Remember checkbox starts unchecked. Cancelling either panel returns before worker submission, so it starts no guest work and does not clear an existing recovery hold. Vault errors remain failures rather than silently falling back to a prompt. Existing explicit opt-in entries may be reused by ordinary operations without prompting. Settings instead always offers a VM/GUID-named replace/forget/cancel choice. Replacement opens fresh native input; checking Remember saves the replacement, while successful input without Remember removes the old entry as disclosed. Cancelling retains the previous entry. Forget is per-user/per-VM and absence is idempotent. These settings perform no guest, power, enrollment or GPU work. Source implementation is complete under APP-005; runtime acceptance remains pending.

Treat adapter error text as untrusted and potentially secret-bearing. Public outcomes use bounded application-owned failure context. Preserve component/stage/numeric-code evidence where safe rather than copy arbitrary stderr into UI/audit output. Diagnostic tracing is opt-in through trusted fixed product paths and runs only in elevated processes; ordinary frontends skip trace-file creation so read-only artifact checks do not require protected write access. Local qualification records must exclude secrets.

## Operation recovery

The [store records](../src/configuration_store.rs) distinguish effect recovery from configuration publication.

VM-bound operation and native-provider holds block only their recorded VM. New operations retain a separate protected receipt for each VM under the existing host operation lock; they do not overwrite, replay or retire another VM's evidence. Reconciliation and save-only resolve the exact original operation ID and retire only its bound receipt after durable terminal audit. Legacy singleton receipts are scoped by their validated VM identity and move only through audited copy/readback/marker publication before an admitted VM operation; interrupted migration retains the original until the identical copy is confirmed. A protected version marker makes older singleton readers fail closed while per-VM receipts exist. Unreadable, inconsistent, duplicate or unknown-scope records remain global blockers, as do unfinished shared authority/configuration imports. Profile deletion is a separately confirmed exception for the selected VM's app records: it binds their complete revision snapshot and discards their recovery records, while preserving unrelated profiles and receipts. The storage/admission correction is implemented in source. | Phase | Meaning | Permitted response |
|---|---|---|
| `Admitted` | Bound operation persisted before effects | Establish current facts independently; do not assume it is safe to replay |
| `EffectsStarted` | Effects may have occurred; terminal outcome not established | Explicit reconciliation from fresh host/guest/recovery evidence; partial/mismatched state remains blocked |
| `Verified` | Independently verified outcome recorded | Retry only the bound save, after checking state/revision/driver/payload consistency |
| `Published` | Bound configuration publication recorded | Confirm the completed publication and safely retire the record |


**Delete profile** is a separately confirmed app-record deletion, available during recovery and independently of VM power or current GPU attachment. Its fresh review binds the enrolled operator and exact VM/GPU pair, all saved-profile/history revisions, and the selected profile's fixed-name operation/provider recovery files. Confirmation explicitly discards that profile's saved settings, pairing, managed history and interrupted-operation records; it does not establish the interrupted operation's outcome. No VM inspection, power change, GPU detachment, driver removal or guest access is dispatched by deletion. Other profiles and unrelated recovery files are retained. Legacy singleton receipts are deleted only when their contents bind this exact VM. An interrupted batch import loses only this profile's document, so resuming it cannot recreate the deleted profile; other imported documents and their progress remain intact. Unknown/shared records without this profile binding are left alone. The common worker lock, mandatory audit, protected file checks, durable deletion progress and revision/readback checks remain in force. Interrupted deletion resumes only its recorded scope and refuses changed/recreated files. Another unfinished enrollment/deletion cannot be overwritten by a fresh request. Ordinary GPU effects still require enrollment and fresh review after a profile has been deleted.

The separate host-restoration **Remove partial GPU setup** worker disposition retains its exact VM/GPU/journal and shutdown checks. It is not the profile-deletion action offered in the interrupted-operation dialog.

An `Admitted` attempt has no dispatched guest/Hyper-V effects. Its GUI review offers **Check recorded outcome**, without guest credential collection or power approval. **Delete profile** remains available as the distinct destructive app-record action. The existing worker still independently checks the recorded starting host state and configuration revision before ending recovery; drift retains the hold. For recovery that does require power changes, the review states the expected final power and that selecting **Check recorded outcome** approves those reviewed changes. Apply and standalone verification reviews retain their existing checkbox controls. These presentation rules grant no authority beyond the existing authenticated, revision-bound worker checks.

Native provider admission is separate from workflow outcome. New markers capture VM/GPU, exact stage, before facts and requested effect, workflow/configuration tokens, existing job identities and a typed COM failure where available. A missing job reference or unreadable/expired job never permits automatic marker removal. From an administrator console, correlate a surviving local terminal job with the original invocation, then run `hyper-gpu-support native-review --job 'Msvm_ConcreteJob.InstanceID="JOB-ID"'`. The supported review validates the job's affected VM, provider job type, new identity, terminal result, compatible before/after host facts and quiescent job inventory. Inspect its original/fresh facts and returned token before separately approving `hyper-gpu-support native-reconcile --review TOKEN`.

The confirmation uses protected captured terminal evidence if that job has since expired; provider access errors do not count as absence. It rechecks workflow/configuration bindings and exact fresh readback, archives the original marker and terminal result, and retires only provider admission. It does not certify workflow success, save desired intent or replay effects. Without sufficient independent completion evidence (including legacy records lacking scope), preserve the native marker, workflow records and Hyper-V event logs for administrator/provider support. Never manufacture a terminal receipt, delete an uncertain marker or infer completion from instantaneous matching state. Hyper-V job-type/terminal metadata follows the [Microsoft provider contract](https://learn.microsoft.com/en-us/windows/win32/hyperv_v2/msvm-concretejob).


## Qualification limits

Historical incident notes do not establish a current host-lockup cause or permanent fix. This reset imports no old milestone completion or active hold. Future live work needs its own scoped authorization and evidence. Automated IPC/fault tests validate selected software boundaries; they do not establish host stability or concurrent GPU sharing.
