# Security and recovery

This page owns product authority/trust boundaries and recovery semantics. [AGENTS.md](../AGENTS.md) owns agent authorization rules; [testing](ENGINEERING.md#validation-and-live-acceptance) owns qualification scenarios. These are contracts to preserve and validate, not a claim that static review proves their enforcement.

## Authority and trust

- Protected enrollment binds the initiating operator, exact existing VM GUIDs/GPU interfaces, and installed artifact identities. Runtime intent, observed attachment, or a GUI draft cannot grant that authority.
- Routine artifact reinstall preserves the existing operator and exact pair identities under the common lock before changing existing permissions or task availability. It rejects authority replacement; a durable package-bound receipt preserves interrupted policy/pending-pair publication and archives readback before releasing installation admission.
- Additive enrollment reviews the current policy revision and operator, appends one pair, and preserves others. GPU replacement is a distinct unavailable transition. Initial setup reviews a fixed four-artifact package and keeps package inputs locked across elevation.
- Elevated setup and worker entrypoints accept fixed typed operations, validated session identities, and authenticated peer processes. Preserve operator SID checks, process binding, local pipe restrictions, frame/output limits, and deadlines. Do not substitute an owner-SID check for exact launched-process authentication.
- Privileged directories/files require trusted ownership, restrictive permissions, and reparse/path checks. Fixed destinations come from Windows known folders. A configuration import or save cannot name an arbitrary privileged destination.
- Installed artifacts are hash-bound to enrollment. Driver payload trust uses Windows signatures/catalog membership and per-file integrity; the mere presence of a catalog is insufficient.
- Effects revalidate fresh enrollment, target identity, provider limits, power, conflicts, driver/payload identity, and the reviewed plan under the protected operation lock. Never execute an old approved plan merely because its displayed summary has not changed.

The relevant implementations are [runner](../src/worker/runner/mod.rs), [worker](../src/worker.rs), [setup](../src/setup.rs), [session pipes](../src/windows_pipe/session.rs), [security](../src/security.rs), and [trust](../src/trust.rs). APP-007 audits concrete trust/recovery gaps in the agreed workflow; APP-008 validates meaningful failure coverage.

## Guest OS eligibility before installation

Only positively identified Windows 11 clients may receive GPU installation, a changed driver payload or an explicit Repair / Reinstall. Compatibility is an installation boundary, not a discovery prerequisite. Startup, discovery, refresh, review, ordinary allocation/toggle changes with unchanged preparation, disable and verification-only work do not open a compatibility session. Read-only review authenticates the host payload and lists the required lifecycle; OS approval is obtained only during the consented Apply. The GUI prepares this scope internally and goes straight into execution for the selected foreground action, without a review dialog or second confirmation. Selecting Apply, Verify, Repair/Reinstall or removal approves that action's required VM power transitions; lifecycle facts appear on progress. Credentials are acquired locally after successful preparation, with existing explicit vault opt-in. CLI planning/approval arguments remain unchanged.

The authoritative observation is the current running OS in an authenticated PowerShell Direct session bound to the exact enrolled VM GUID. It reads `Win32_OperatingSystem` version, build and ProductType, plus the current `InstallationType`. Version and build must agree; a recognised Windows 11 build, workstation ProductType and Client installation are required. ProductName, VM names, UI icons, local display caches, old preparation receipts and Hyper-V KVP reports do not prove current eligibility. Windows 11 can retain a Windows 10 ProductName, so product-name text is deliberately absent from this decision. A failed live query never falls back to historical metadata.

For an **already running** VM, the OS query precedes workflow journal changes, shutdown, GPU changes and guest installation. A refusal is marked as a pre-effect compatibility block. For an **off VM**, the prepared setup scope includes a temporary start, read-only identification and graceful shutdown before GPU changes. The existing protected operation receipt and per-VM pending journal are written before starting it; `preparation_started=false` preserves the distinction between identification and installation. The old completed preparation receipt is retained until identification succeeds. Failure attempts graceful restoration to Off only after fresh VM/GPU/journal facts permit it. An uncertain start, changed facts, refused shutdown or failed restoration retains recovery. No force-off, unlock, implicit retry or automatic hold retirement is permitted. A successful power restoration after refusal also retains the bound operation for explicit recovery review.

There is no offline disk attachment, partition-layout assumption or hive loading. An encrypted Windows 11 VM can boot and unlock through its normal guest configuration, then be identified through the same session as an unencrypted VM. The application never requests BitLocker keys or alters encryption/security settings. If the guest waits for recovery, cannot finish startup, has unavailable PowerShell Direct, rejects credentials or supplies incomplete/inconsistent facts, installation is blocked as unidentified. An unsupported running Windows release is rejected as unsupported. A guest such as Linux that cannot provide the Windows session remains unidentified and cannot receive installation. Metadata absence does not prevent reaching the live check; metadata presence cannot override it.

After admission, preparation still checks the current OS **inside its actual session before bootstrap, file transfer or launch**, and the guest worker checks again before driver writes. Thus an OS change across a preparation reboot cannot authorise writes with earlier evidence. These defences reject Server and Windows PE even when their builds match a client. Removal of host GPU support remains available without guest compatibility or credentials.

[Guest compatibility](../src/guest_compatibility.rs) owns release policy independently of observation and workflow. New OS support must add its identification/transport and installation support, then extend this central policy and its negative tests; display classifiers never grant support. Unknown releases are blocked until deliberately added. The [guest transport](../src/guest.rs) and [local guest OS reader](../src/guest/os.rs) supply facts, while the [workflow](../src/workflow/apply.rs) owns consented power and recovery. Failures use typed, application-owned reasons without provider strings, paths or credentials.

Microsoft contracts: [PowerShell Direct requirements](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/powershell-direct), [current OS facts](https://learn.microsoft.com/en-us/windows/win32/cimwin32prov/win32-operatingsystem), [Windows 11 release builds](https://learn.microsoft.com/en-us/windows/release-health/windows11-release-information), [intrinsic KVP schema](https://learn.microsoft.com/en-us/windows/win32/hyperv_v2/msvm-kvpexchangedataitem) and [Data Exchange persistence](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/integration-services-data-exchange).

## Credentials and diagnostics

Credentials are obtained locally, retained only through explicit Windows Credential Manager opt-in, and kept out of desired configuration, journals, audits, public reports, and persistent recovery. Before the prompt, name the selected VM and clearly explain that its Windows credentials are needed, not the host computer's credentials. A credentials settings action does not establish guest connectivity or graphics health. Credential deletion does not revoke pairing.

The shared native prompt path requires acknowledgement of a named-VM explanation before collecting input. Acknowledgement does not authorize remembering; the native Remember checkbox starts unchecked. Cancelling either panel returns before worker submission, so it starts no guest work and does not clear an existing recovery hold. Vault errors remain failures rather than silently falling back to a prompt. Existing explicit opt-in entries may be reused by ordinary operations without prompting. Settings instead always offers a VM/GUID-named replace/forget/cancel choice. Replacement opens fresh native input; checking Remember saves the replacement, while successful input without Remember removes the old entry as disclosed. Cancelling retains the previous entry. Forget is per-user/per-VM and absence is idempotent. These settings perform no guest, power, enrollment or GPU work. Source implementation is complete under APP-005; runtime acceptance remains pending.

Treat adapter error text as untrusted and potentially secret-bearing. Public outcomes use bounded application-owned failure context. Preserve component/stage/numeric-code evidence where safe rather than copy arbitrary stderr into UI/audit output. Diagnostic tracing is opt-in through trusted fixed product paths and runs only in elevated processes; ordinary frontends skip trace-file creation so read-only artifact checks do not require protected write access. Local qualification records must exclude secrets.

## Operation recovery

The [store records](../src/configuration_store.rs) distinguish effect recovery from configuration publication.

VM-bound operation and native-provider holds block only their recorded VM. New operations retain a separate protected receipt for each VM under the existing host operation lock; they do not overwrite, replay or retire another VM's evidence. Reconciliation and save-only resolve the exact original operation ID and retire only its bound receipt after durable terminal audit. Legacy singleton receipts are scoped by their validated VM identity and move only through audited copy/readback/marker publication before an admitted VM operation; interrupted migration retains the original until the identical copy is confirmed. A protected version marker makes older singleton readers fail closed while per-VM receipts exist. Unreadable, inconsistent, duplicate or unknown-scope records remain global blockers, as do unfinished shared authority/configuration imports. Profile deletion is a separately confirmed exception for the selected VM's app records: it binds their complete revision snapshot and discards their recovery records, while preserving unrelated profiles and receipts. The storage/admission correction is implemented in source. Evidence: `local/evidence/m1-gate-20261016T095622924Z/`. The six native XML/COM metadata tests and their fixtures were deleted at the user's request; runtime metadata handling is unchanged, and this gate used no test exclusion. Product installation and live multi-VM acceptance remain pending.


| Phase | Meaning | Permitted response |
|---|---|---|
| `Admitted` | Bound operation persisted before effects | Establish current facts independently; do not assume it is safe to replay |
| `EffectsStarted` | Effects may have occurred; terminal outcome not established | Explicit reconciliation from fresh host/guest/recovery evidence; partial/mismatched state remains blocked |
| `Verified` | Independently verified outcome recorded | Retry only the bound save, after checking state/revision/driver/payload consistency |
| `Published` | Bound configuration publication recorded | Confirm the completed publication and safely retire the record |


**Delete profile** is an explicitly selected app-record deletion, available during recovery and independently of VM power or current GPU attachment. Its fresh review binds the enrolled operator and exact VM/GPU pair, all saved-profile/history revisions, and the selected profile's fixed-name operation/provider recovery files. Selecting Delete profile explicitly discards that profile's saved settings, pairing, managed history and interrupted-operation records; it does not establish the interrupted operation's outcome. No VM inspection, power change, GPU detachment, driver removal or guest access is dispatched by deletion. Other profiles and unrelated recovery files are retained. Legacy singleton receipts are deleted only when their contents bind this exact VM. An interrupted batch import loses only this profile's document, so resuming it cannot recreate the deleted profile; other imported documents and their progress remain intact. Unknown/shared records without this profile binding are left alone. The common worker lock, mandatory audit, protected file checks, durable deletion progress and revision/readback checks remain in force. Interrupted deletion resumes only its recorded scope and refuses changed/recreated files. Another unfinished enrollment/deletion cannot be overwritten by a fresh request. Ordinary GPU effects still require enrollment and fresh review after a profile has been deleted.

The separate host-restoration **Remove partial GPU setup** worker disposition retains its exact VM/GPU/journal and shutdown checks. It is not the profile-deletion action offered in the interrupted-operation dialog.

An `Admitted` attempt has no dispatched guest/Hyper-V effects. The explicit foreground recovery action directly checks its recorded outcome, without guest credentials or power changes. **Delete profile** remains a distinct explicitly selected app-record action. The worker independently checks recorded host state/configuration before ending recovery; drift retains the hold. Recovery that actually requires guest/power work includes those transitions under the foreground action and displays the expected final power on progress. There are no separate GUI review dialogs or power-consent checkboxes. Fresh plan/revision/identity binding, Windows prompts and protected worker checks remain mandatory. Refresh, polling and result publication never automatically enter recovery or replay Apply. Native provider admission/administrator reconciliation remains a separate domain with its original evidence requirements. These UI changes do not authorize live effects during source/build validation.

Native provider admission is separate from workflow outcome. New markers capture VM/GPU, exact stage, before facts and requested effect, workflow/configuration tokens, existing job identities and a typed COM failure where available. A missing job reference or unreadable/expired job never permits automatic marker removal. From an administrator console, correlate a surviving local terminal job with the original invocation, then run `hyper-gpu-support native-review --job 'Msvm_ConcreteJob.InstanceID="JOB-ID"'`. The supported review validates the job's affected VM, provider job type, new identity, terminal result, compatible before/after host facts and quiescent job inventory. Inspect its original/fresh facts and returned token before separately approving `hyper-gpu-support native-reconcile --review TOKEN`.

The confirmation uses protected captured terminal evidence if that job has since expired; provider access errors do not count as absence. It rechecks workflow/configuration bindings and exact fresh readback, archives the original marker and terminal result, and retires only provider admission. It does not certify workflow success, save desired intent or replay effects. Without sufficient independent completion evidence (including legacy records lacking scope), preserve the native marker, workflow records and Hyper-V event logs for administrator/provider support. Never manufacture a terminal receipt, delete an uncertain marker or infer completion from instantaneous matching state. Hyper-V job-type/terminal metadata follows the [Microsoft provider contract](https://learn.microsoft.com/en-us/windows/win32/hyperv_v2/msvm-concretejob).


## Qualification limits

Historical incident notes do not establish a current host-lockup cause or permanent fix. This reset imports no old milestone completion or active hold. Future live work needs its own scoped authorization and evidence. Automated IPC/fault tests validate selected software boundaries; they do not establish host stability or concurrent GPU sharing.
