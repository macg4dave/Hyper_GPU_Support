# GUI guide

This page describes the agreed workflow from the user Q&A. [Baseline](BASELINE.md) records current implementation gaps. Keep the existing [Slint design](../src/gui/ui/app.slint) and wire behavior through the shared Rust core.

## Purpose and controls

Select a supported existing VM, toggle GPU support, and select GPU VRAM from 1 GB to the selected card's physical capacity. Hyper-V handles VM creation, system RAM, and general management. No automatic balancing or full-capacity warning policy is required now.

The existing Dashboard, System, Settings, About, and dialog design remain the foundation. Preserve stable selection, keyboard navigation, scrolling, themes, focus, and responsive progress.

Windows exposure repainting now has a source backport in the pinned Slint 1.18.1 winit backend. Before each Windows draw, the backend includes the native pending update region in Slint's renderer damage, so returning from partially off-screen or taskbar-covered positions can repaint current content even without another UI property change. This uses native repaint events and adds no periodic refresh. See the [local backend patch](../vendor/i-slint-backend-winit/LOCAL_PATCH.md) for provenance and validation: production test compilation, two in-memory repaint regressions and 56 GUI controller/startup tests passed on 11 October 2026. All Windows redraw bugs are closed by explicit user acceptance on that date after a successful live taskbar/off-screen check through Slint MCP and direct user observation. The separate workflow test's VRAM expectation still fails the wider automated gate.

APP-002 source now displays the 1 GB-to-card-capacity slider, with exact physical endpoints. [APP-011](BACKLOG.md#app-011--correct-physical-vram-and-provider-mapping) removes reported partition metadata as a VRAM byte ceiling. The selected physical capacity bounds the slider; unknown capacity remains unavailable. Hyper-V decides whether the byte request is accepted, followed by exact readback. Existing requests below 1 GB remain labeled exactly; moving the slider is an explicit edit, not a rewrite on load. Advanced Allocation retains exact VRAM fields for compatibility and correction. Compute/Encode/Decode editors are removed from this GUI; saved requests are preserved and shown in review. Use the toggle or More actions > Remove GPU support to disable support. Compilation and isolated boundary/controller checks passed M1; rendering and real hardware acceptance remain pending.

## Review and Apply

Toggle/VRAM changes remain drafts. Apply opens a review panel naming the selected VM, showing what will change and relevant time warnings, and explaining every required start, shutdown, or restart. Show the expected final power state. A second Apply confirms; cancellation returns to editing.

The memory review displays exact observed/planned minimum, optimal and maximum bytes. Displayed requests do not establish enforced quotas or reserved memory. The metadata-ceiling removal and its regression tests await runtime validation.

Review must reflect a fresh backend plan. Changed target or inputs invalidate approval. Setup/enrollment authority remains distinct from GPU effects, even when presented as one understandable setup journey.

APP-003 source now provides first Apply → review → second Apply, with Cancel retaining the draft and clearing approval. Review shows ordered backend steps, changed compatibility values, final power, and relevant time warnings. It binds the original committed revision as well as the VM and draft; the protected worker independently rechecks backend state before effects. Initial setup now includes its final shutdown under APP-004; ordinary changes now skip guest work and finish off under APP-006. M1 source review and non-hardware checks passed; real interaction acceptance awaits APP-009.

## First GPU setup

The application manages required VM power transitions, guest preparation, GPU configuration, and initial verification. Review explains the actual sequence before confirmation. Show a clear verification pass/fail for the selected VM. After completed setup and verification, gracefully shut the VM down and leave it off for the user to start through Hyper-V.

Before the local credential prompt, show a friendly explanation such as: “Setup needs the Windows sign-in for this VM. Use the account inside the VM, rather than the account for your host computer.” Include the actual VM name. Remembering credentials is optional and requires explicit opt-in.

APP-005 source now presents a blocking local Windows explanation panel before the native username/password dialog, naming the reviewed VM and explaining its guest administrator account. OK opens credential entry; Cancel stops the request before any guest operation starts. Remember begins unchecked and stores credentials only when explicitly selected, in this user's Windows Credential Manager for that VM. Existing stored credentials can be reused without opening either panel. Settings uses the same path and does not check guest connectivity. Cancel retains pending edits, clears an Apply/Verify review, and leaves any existing recovery hold intact. Isolated dialog/cancellation regressions passed M1; real native interactions await APP-009.

An interrupted or failed operation must not pretend setup completed or promise a final power state that has not been confirmed.

APP-004 source now identifies initial setup when completed preparation and graphics receipts are absent. Existing completed receipts remain valid historical setup evidence; an attachment or standalone graphics check alone does not establish preparation. Package setup/additive enrollment retain their existing separate reviews, followed by a fresh GPU effect review. Initial setup success requires graphics pass and confirmed final-off readback; its completion message names the VM and tells the user to start it through Hyper-V. A publication failure reports the guest setup result separately and offers save-only retry. Interrupted effects retain recovery with the reviewed final power; reconciliation does not repeat preparation/assignment/allocation. Compilation and isolated lifecycle/recovery tests passed M1; rendering and real VM qualification remain pending.

The first-time setup card now stages enabled support and opens the existing enrollment/setup review. It remains unavailable while eligibility or recovery blocks the selected VM; clicking it alone grants no effect authority. Real interaction is pending validation.

## Later changes

Enable/disable and VRAM changes follow review and Apply, without repeating full preparation or initial graphics verification. Retain necessary validation and readback, and show the actual result. Required shutdown/restart is managed by the application and disclosed in review. Successful ordinary changes always leave the VM off, whether it started running or stopped. The user starts it through Hyper-V.

If preparation becomes invalid or the signed driver payload changes, review explicitly identifies required setup/update, its preparation/graphics steps, credentials and time warnings before confirmation. Matching completed preparation/graphics receipts permit ordinary changes without repeating those steps. Ordinary success confirms host readback and final-off state; it does not claim a fresh rendering pass. Interrupted ordinary changes are reconciled from host readback without guest access or temporary boot; partial state retains recovery. APP-006 source and non-hardware gate passed; live acceptance remains pending.

## State and failures

Keep saved settings, pending edits, actual observations, and the last initial verification result distinct. Preserve drafts through refresh conflicts and require resolution before effects. Busy/modal states prevent conflicting actions.

APP-016 source labels an enrolled VM as Authorized: permission to manage its recorded VM/GPU pair does not verify guest drivers. Attachment remains a separate host observation. Previously prepared state now explicitly says current guest files and driver parity are unknown, since a checkpoint rollback can undo guest setup. The last successful graphics timestamp remains history, not current health. Reopening and Refresh do not access the guest or automatically repair it. Compilation, regression execution and visual acceptance for this change remain pending.

The rollback recovery fixes are tracked separately in [APP-017 through APP-023](BACKLOG.md#app-017--report-saved-versus-observed-host-configuration-differences). APP-018 source extends explicit Verify to compare current guest payload files and the guest preparation receipt before checking graphics. APP-020 replaces More actions' Reapply / Update control with explicit Repair / Reinstall. GPU-off provides host removal through reviewed Apply where recovery permits it; APP-022 connects Forget pairing after inactive host-state admission. These paths must not be presented as a completed rollback repair workflow.

APP-019 source presents the latest guest check separately from historical successful rendering. Failed, unavailable and incomplete checks no longer allow historical success to skip verification; proven payload mismatch requires preparation on a later reviewed operation after recovery permits it. A passed guest check does not remove a lifecycle/recovery hold. Historical timestamps remain visible as history. Compilation, regression execution and visual acceptance are pending.

APP-020 source adds Repair / Reinstall for an authorized pair. It enables the existing draft while preserving its resource categories and opens a fresh review explicitly requesting complete current signed driver preparation, payload/receipt and selected-hardware graphics verification, and final-off completion. Historical receipts cannot skip the sequence; independently matching guest files may be retained. Confirm with the second Apply and any required downtime approval; Cancel discards the review without driver/VM effects. Selection, draft or saved revision changes invalidate approval. Pending recovery must be reconciled first. Ordinary Apply never inherits the repair flag. This source has not been compiled, rendered or exercised; installed packages are unchanged.

The review fixes add safe exits through the existing Recovery / Reconcile action: a terminal failed Verify with independently confirmed restoration can end while retaining failure, permitting a subsequent reviewed repair. Refused initial setup/reinstall shutdown can end when fresh facts establish no preparation entry and unchanged original host state/history. These candidates require no fresh guest check or credentials; changed or uncertain facts remain blocked. The completion message explicitly avoids claiming guest setup/rendering success. Verify will not restart a guest stopped externally during a check. Source-only; real interaction remains unvalidated.

APP-021 source adds More actions > Remove GPU support. It stages the existing off toggle and opens review for the exact authorized pair. Review lists actual host detach/settings/power changes and final-off completion, without guest credentials or rendering checks. Missing guest setup and an already missing adapter are supported; pending recovery, unrelated hardware and stale approvals remain blocked. Removal preserves guest files, product authorization, setup/graphics history and retained resource requests. Each compatibility field still owned by the product is restored; externally changed values are kept, and successful removal releases ownership. APP-022 separately removes inactive authorization/profile records. Source formatting/diff checks passed; compilation, tests and real interaction remain pending.

APP-022 source connects More actions > Forget pairing after completed GPU removal. It separately reviews deletion of this VM's product authorization, saved settings and managed setup/verification journal; Windows elevation follows confirmation. Cancel preserves records. The VM must already be off without GPU support; active intent, pending drafts, recovery, unreadable history or stale revisions remain blocked. It does not uninstall guest drivers, delete the VM/disks/checkpoints, affect other profiles or remove shared package artifacts. Successful refresh leaves the VM discoverable and unconfigured; enabling support requires a new reviewed enrollment/setup. Interrupted removal is shown through Recovery with explicit remaining-record deletion consent and fresh bound readback, rather than claiming completion. The Delete profile wording/guided active-support flow is still APP-024. This source has not been compiled, rendered or exercised.

APP-017 source adds expected-versus-observed host configuration differences to the selected VM's support summary. It uses committed settings and the latest Hyper-V read, with managed compatibility history identified as its baseline. Missing/wrong GPU attachments and changed explicit resource/settings values are listed. Missing or unreadable intent, stale/incomplete observations, omitted resource requests and unavailable baselines remain Unknown. Disabled saved intent with no attachment is consistent. This read-only comparison neither accesses the guest nor diagnoses rollback; repair/removal still requires the existing review and protected admission. Compilation passed in APP-018's all-target check; regression execution and visual acceptance remain pending.

Verify's review now names the current authenticated payload digest and explains that guest administrator credentials are used to hash current driver destinations, compare the receipt and check device health/rendering. An off guest is temporarily started and gracefully restored to off; a running guest stays running. Verify refreshes its protected helper executables, verification metadata/lock and optional diagnostics. It does not reinstall driver files, rewrite the preparation receipt, change host GPU settings or save desired intent. Missing/changed files and mismatched receipts differ from denied, unavailable or timed-out observations; none proves the origin was checkpoint rollback. An absent selected host attachment blocks the check with a reviewed-change/removal instruction. Compilation passed under APP-018; regression execution, real interaction and behavioral acceptance remain pending.

Progress names actual stages and explains delays plainly. Failed configuration publication offers bound save-only retry; uncertain effects require explicit reconciliation. Do not replay GPU work or clear recovery to make a status look successful.

When an unfinished operation blocks More actions, the dialog names the affected VM and offers **Review recovery**. Verify, Repair / Reinstall, Remove GPU support and Forget pairing use the same explanation before changing drafts or starting a new review. The button opens the existing recovery review; it does not confirm recovery or clear a hold. Edits remain intact. This presentation change is source implemented; compilation, automated regression execution and real interaction validation are pending.

Current-source review additionally blocks new editing/reviews when the selected journal requires recovery, even without a loaded save record. Failed controller state/recovery reads remain visible and disable execution instead of being replaced by a completion dialog. Installed worker availability is checked in background jobs; admission still performs fresh authentication. See the [review record](evidence/m1-source-review.md) for validation limits.

## Validation

The [M1 non-hardware gate](evidence/m1-closure.md) passed on 11 October 2026. No GUI render, live interaction or native credential dialog was exercised; those remain APP-009 acceptance.

Live launch can request elevation. Real GUI checks belong to the authorized APP-009 run, not a harmless visual launch. Legacy mock/snapshot tooling was removed from source under APP-001. Removal compiled and passed startup-dispatch tests under M1; real visual acceptance remains pending. It is not a preview or testing path.


During refresh failures, the GUI retains editable drafts and shows unavailable status rather than internal historical-mode labels. Apply still requires refreshed observations and protected review. First-install discovery is refreshed explicitly until enrollment enables protected polling. The sidebar footer label and Help button have been removed at the user's request. The top-right "VIRTUAL MACHINES" header label is also removed in source; visual validation of this text-only change is pending.

Guest sign-in copy now uses the friendly VM name, explains the administrator account and purpose in plain language, and gives a short optional Remember explanation. It omits the VM ID and repeated technical details. Text-only follow-up; no live prompt rerun was requested.

APP-012 source now displays acknowledged file-transfer sizes in decimal KB/MB/GB with a percentage and file count, updating a single running row. For example: `Copying files: 1.7 GB of 3.4 GB (50%); 140 of 273 files; verification pending`. Reaching 100% means all bytes were acknowledged; preparation and graphics verification still have their own outcomes. Stage completion and failures remain visible. This follow-up has not yet been built or visually checked.
