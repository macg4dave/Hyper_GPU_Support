## Checkpoint rollback investigation

User-reported reproduction (11 October 2026): enroll/setup GPU support, restore a guest checkpoint from before GPU drivers were installed, then reopen. The report says enrollment still appears successful, Verify does not work correctly, and recovery controls are unavailable. This investigation inspected source only; no checkpoint, guest access or application launch was performed and the exact live Verify failure remains unconfirmed.

[Runner](../src/runner.rs) stores protected `enrollment.json` on the host: operator, exact VM/GPU pairs and installed artifact identities. Its per-VM `<vm-guid>.json` workflow journal also lives on the host and retains `prepared` (payload digest), `last_verified` (historical graphics-check timestamp), ownership settings and pending recovery. Saved `<vm-guid>.toml` files separately record intent. These records are not guest-disk state and the reported rollback does not invalidate them automatically.

[Workflow](../src/workflow.rs) decides whether setup is required by comparing the current host payload digest with the journal and checking for historical preparation/graphics receipts. It does not inspect current guest files in the read-only Apply plan. Consequently, unchanged receipts can select ordinary Apply after a guest rollback. The ordinary GUI Apply path reviews that same plan. APP-020 adds a separate explicit Repair / Reinstall request through the same worker, described below.

Before APP-018, explicit Verify performed fresh guest device-health and selected-hardware rendering through [guest code](../src/guest.rs), without comparing the complete driver manifest with current guest files. APP-018 closes that source gap below. Verify still requires the selected stable host GPU assignment, and failures leave a pending journal with previous success fields retained (APP-019). The transport bootstraps authenticated guest helper executables even in Verify mode. These are source-backed facts and possible failure paths, not a diagnosis of the unobserved runtime error.

GPU-off already uses shared disable logic: detach the selected adapter, restore only owned compatibility settings, check host readback and finish off, without preparing or verifying guest graphics. Pending recovery and unrelated assignments still block effects. APP-021 exposes this as Remove GPU support, with per-field ownership restoration and explicit ownership release after successful removal. APP-022 now connects the inactive Forget pairing transition; APP-020 separately provides explicit same-digest repair.

APP-016 source changes label host authority as Authorized, explain that authorization does not verify guest drivers, and explicitly mark prior preparation as uncertain after checkpoint rollback. Graphics timestamps remain historical; no rollback is inferred or authority revoked. Added regression source is unrun. [APP-017 through APP-023](BACKLOG.md#app-017--report-saved-versus-observed-host-configuration-differences) separate detection, stale-result handling, reinstall, removal and qualification. Compilation, new test execution and real interaction remain pending; M1's previous gate does not validate these changes.

It compares committed intent, never enrollment settings or drafts, with fresh attachment and explicit resource readback; applicable managed journal settings provide a separately identified compatibility baseline. Historical/incomplete observations and unavailable intent/baselines remain Unknown. A missing adapter does not newly block reviewed edits; unrelated adapters retain existing refusal. Isolated regression source is added but unrun; compilation and visual validation remain pending. This comparison does not inspect guest files or establish checkpoint rollback.

Guest checks validate manifest/GPU membership, independently hash every current destination, and compare the guest receipt with that digest, file count and current machine identity. Missing/changed files and mismatched receipts remain distinct from denied/unavailable/timed-out facts and graphics failures. The disclosed helper bootstrap, verification metadata/lock and optional diagnostics can write to the protected helper directory, but Verify does not transfer driver payloads, rewrite preparation receipts or publish intent. Matching host receipts cannot skip the check. Existing lifecycle restoration and recovery holds remain; latest-outcome persistence/eligibility is APP-019. `cargo check --locked --all-targets` passed; isolated regression execution and live checks remain pending.
