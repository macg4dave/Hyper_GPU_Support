# Architecture

This page owns component and data-flow boundaries. The [roadmap](roadmap.md) and [backlog](backlog.md) record current delivery status; [security](SECURITY.md) owns trust/recovery rules; [configuration](CONFIGURATION.md) owns formats and persistence.

The default application is `hyper-gpu-support.exe`. Setup currently expects that executable plus `hyper-gpu-runner.exe`, `hyper-gpu-guest.exe`, and `d3d11-probe.exe` in the same package directory. Internal setup/worker modes reuse the application executable; they are fixed protocol entrypoints, not general command execution. The installed runner is separate from the initiating user frontend.

The protected runner lives in `src/worker/runner/`; `lib.rs` re-exports it as `runner`, preserving existing callers. Its private modules separate [protocol types and framing](../src/worker/runner/protocol.rs), [authenticated IPC and admission](../src/worker/runner/ipc.rs), [secret-free audit](../src/worker/runner/audit.rs), [enrollment policy and artifact checks](../src/worker/runner/policy.rs), [pair authority](../src/worker/runner/pairing.rs), [installation and setup recovery](../src/worker/runner/installation.rs), [task scheduling](../src/worker/runner/scheduler.rs), [protected storage and locking](../src/worker/runner/storage.rs), and the [native workflow backend](../src/worker/runner/backend.rs). The existing [operation recovery](../src/worker/runner/recovery.rs), [artifact reinstall](../src/worker/runner/reinstall.rs), and [profile removal](../src/worker/runner/profile_removal.rs) modules retain their responsibilities. Tests stay with the owning responsibility. This is a structural change: protocol formats, public entrypoints, admission/effect order, errors and recovery rules are unchanged.

The live controller lives in `src/gui/live/`. Its `mod.rs` retains the existing `run`, `Source` and startup-completion interfaces and owns lifecycle coordination and the shared `Arc<Mutex<State>>` alias. `editor` registers selection/draft callbacks; `actions` dispatches user actions to focused operation modules. `background` owns task admission and event-loop delivery, `state_access` handles locking/completion failures, and `refresh` publishes inventory and preserves VM-bound results. Each operation module keeps its review, confirmation and failure/readback handling together. Siblings use explicit imports rather than a controller-wide wildcard or a new service abstraction. The existing presentation, source, polling, installation and progress helpers retain their responsibilities; only event-loop callbacks update Slint models. The source adapter continues to reuse the protected runner/worker contracts. This is a structural refactor: public interfaces, errors, scheduling, consent, approval and recovery behavior are preserved. The completed refactor passed the full non-hardware gate on 16 October 2026, including 259 core tests, 135 frontend tests, five UI-text integration tests, strict Clippy and product binary builds. This includes two new headless callback regressions for draft retention and review cancellation. Installed GUI and VM/GPU acceptance remain separate.

The [live-state module](../src/gui/live_state/mod.rs) retains the existing controller-facing `State`, review/readback types and helper exports. Its private modules separate [inventory and stable selection](../src/gui/live_state/inventory.rs), [allocation drafts and eligibility](../src/gui/live_state/draft.rs), [saved intent and conflicts](../src/gui/live_state/configuration.rs), [recovery and operation readback](../src/gui/live_state/recovery.rs), [approval binding and invalidation](../src/gui/live_state/review.rs), [profile deletion](../src/gui/live_state/profile.rs), and [review text](../src/gui/live_state/review_text.rs). Shared state stays in `mod.rs`; modules add focused `State` implementations without introducing new ownership layers or effect adapters. The [regression tests](../src/gui/live_state/tests/mod.rs) are grouped by responsibility and share in-memory fixtures. This is a structural refactor: interfaces, errors, approval rules and recovery behavior are preserved. Automated validation passed the full non-hardware gate on 16 October 2026; installed GUI and VM/GPU acceptance remain separate.

The GUI keeps a VM-bound [result notice](../src/gui/result_notice.rs) during a completion status retry. It contains presentation text only; no reviewed effect authority is retained. Refresh invalidates effect reviews before restoring a result's continuation. Closing or starting a new review drops the notice.

An explicit recovery action checks the recorded outcome for its bound VM. An `Admitted` receipt selects credential-free, record-only reconciliation; later records use the existing worker recovery path and retain uncertain outcomes. **Delete profile** starts separately from its foreground action, including during recovery or while the VM is running. It discards only the selected profile and interrupted-operation records without invoking Hyper-V or guest adapters; fixed file names, exact revisions, the common lock and resumable deletion progress preserve other profiles. A recovery dialog binds deletion to its named VM even when another VM was previously selected. There is no review confirmation or power checkbox. Worker admission, readback and uncertainty retention remain authoritative.

The fixed guest executable streams bounded `HGPREPARATION` phase labels at actual copied-file check, installation, installed-file check, current guest-file/receipt check and graphics boundaries. The authenticated transport relays those fixed events separately from the final JSON reply. The host [transfer monitor](../src/guest_transfer.rs) validates operation-specific ordering, bounds the phase queue and requires all expected phase boundaries for a successful worker reply. Coalesced byte acknowledgements remain independent. Phase delivery cannot certify success; worker exit, receipt/file readback, graphics and workflow lifecycle/publication checks remain authoritative.

Guest OS compatibility belongs to GPU installation admission, independently of discovery/display metadata. The [release policy](../src/guest_compatibility.rs) evaluates current Windows facts; the authenticated guest transport supplies those facts and the shared workflow owns any explicitly reviewed temporary boot. Planning does not require OS metadata or guest access. Offline disk/hive inspection and KVP admission fallback have been removed. Preparation checks its own session before bootstrap, and the [guest-local reader](../src/guest/os.rs) checks again before driver writes without depending on a host disk adapter. See [security](SECURITY.md#guest-os-eligibility-before-installation) for unknown OS, BitLocker and restoration/recovery behavior.

Read-only preparation can be abandoned without publishing its late result or error. Its background read keeps foreground admission and the visible updating state until it finishes; drafts remain editable. Preliminary planning uses eligible historical preparation evidence without a payload pass, while Apply independently authenticates the current payload and rejects drift before effects. Reopening abandoned preparation does not cache authority or permit replay.

Every in-app modal uses the [shared dialog frame](../src/gui/ui/dialog-frame.slint): a centred neutral surface, common dimensions/padding/heading treatment, scrollable content and fixed footer. [Operation content](../src/gui/ui/install-dialog.slint) and [choices, notices and help](../src/gui/ui/dialogs.slint) share the expandable, selectable and copyable [dialog log](../src/gui/ui/technical-output.slint). More Actions retains its vertical choices. The [display-only header controller](../src/gui/dialog_presentation.rs) selects phase labels from typed operation identity, independently of translated titles. Installation, permission checks/updates/reconciliation, plan building, Apply, Verify, recovery, saving, deletion and reads remain distinct. Readback appears only when it actually starts; terminal failures truncate future phases. Generic notices/help/choices clear previous phases. Apply keeps a fixed planned milestone order, stable completed ticks, sticky failures and the full repeated-event log; completion requires the terminal result and saved-state readback.

Separate review dialogs and their confirmation callbacks are removed. Successful fresh preparation continues directly into execution when the worker is available. Cancelled, failed or stale preparation cannot enter that continuation. Exact target/revision/package binding and worker admission remain. The foreground action authorizes its required power transitions, which appear as facts on the progress screen. Recovery starts only from an explicit recovery action, never from refresh or result publication. Native Windows authentication/UAC prompts remain. The main page layout and settings pages are unchanged; action captions now describe the operation they start. The direct-execution update passed the complete non-hardware gate on 16 October 2026 (`local/evidence/m1-gate-20261016T212301434Z/`): 408 product tests, 12 catalogue tests, strict lint, binary builds and API documentation. Protected installation and independent verification passed (`local/evidence/install-20261016T212326471Z/independent-verification.json`): all four source/installed/policy hashes match, both enrolled targets and 1,223 persistent files were preserved, and the runner is enabled and Ready. Headless render/interaction checks cover both themes at normal and minimum sizes; installed GUI journeys and VM/GPU acceptance remain unrun.

Worker progress identifies VM readback, selected GPU/driver reads and signed-file authentication, including nested reads during admission and final checks. The headline returns to a still-running parent when a nested read ends; when no stage is active it waits for the final reply rather than showing a completed stage as the current work. Ordered event history and stage outcomes remain separate from final readback and publication. These source changes establish no measured performance guarantee.

## Workflow module family

[Workflow root](../src/workflow.rs) retains the shared `Backend` trait and `OperationResult`, with explicit re-exports preserving public and crate-visible caller paths. Its private children own the operation stages:

| Module | Responsibility |
| --- | --- |
| [Journal](../src/workflow/journal.rs) | Durable state, setup eligibility, check persistence/readback and historical success timestamps |
| [Planning](../src/workflow/planning.rs) | Read-only decision gathering, reviewed effects and per-setting restoration calculation |
| [Apply](../src/workflow/apply.rs) | Consumed admission and ordered setup/update, ordinary change, reinstall and removal effects |
| [Verification](../src/workflow/verification.rs) | Explicit Verify admission, current payload checks and operation-specific restoration guards |
| [Reconciliation](../src/workflow/reconciliation.rs) | Independently prove achieved outcomes and recorded lifecycle without replaying Apply |
| [Guest checks](../src/workflow/guest_check.rs) | Shared check classification, restored-negative evidence and graceful power restoration/readback |

Enabled Apply writes compatibility settings only when admitted initial settings differ from the reviewed target. Matching settings still acquire/retain the recorded ownership baseline, and final independent readback remains mandatory (APP-029).

Operation modules depend on the shared contracts/helpers; Verify and reconciliation do not depend on each other's execution. Admission-token fields remain private to their operation modules; planning internals and shared primitives are visible only within the workflow family. The worker still owns authority, authentication, locks, protected receipts, publication and audit. Backend adapters and transport remain outside this family.

Focused tests live inline with their owning module. [Shared doubles/fixtures](../src/workflow/test_support.rs) and [cross-operation scenarios](../src/workflow/tests.rs) are compiled only under `#[cfg(test)]`. Current automated checkpoints and their exclusions are recorded in backlog clearance evidence (historical record; page retired).

## State separation

Startup displays the application name, a temporary monogram icon and the shared progress indicator while six background inventory/configuration reads complete. Progress counts completed reads, not estimated time. Success opens the dashboard; failure retains its error on the splash with a dashboard continuation and the normal Refresh retry. No artificial delay is used.

VM OS icons use optional host KVP `OSName` metadata, never the VM's display name or guest access. Direct XML element reads avoid XPath/type-spelling dependencies; CIM class/property identifiers are matched without case sensitivity; malformed unrelated entries do not suppress a valid OS entry. Missing, conflicting or unrecognised OS metadata uses the generic icon. Inventory refresh updates the existing row model, including OS changes and loss of detection. A single image binding selects bundled Windows, Tux or computer SVG assets; a neutral light plate keeps their colours visible in both themes.

The dashboard's outer viewport owns horizontal scrolling only; the VM list and details own vertical scrolling within the available height. The details scroll extent follows a trailing layout marker rather than relying on the preferred-height report of conditional nested layouts, including expanded allocation, wrapped text and diagnostics. Diagnostics reserve a usable text viewport, scroll offsets clamp after resize/collapse, and actions stay outside the scroll viewport. Operation dialogs share theme-specific neutral surfaces so standard Fluent control fills and states remain distinct. These source contracts do not establish installed visual or live VM acceptance.

VM effect recovery admission and presentation match stable VM IDs. Operation and provider receipts are retained separately for each VM, and the existing common lock still serializes operations. Another VM's held receipt does not block editing, reviewing or applying an enrolled VM's GPU changes; shared authority/import uncertainty and records whose scope cannot be established remain global blockers. The recovery warning and Inspect recovery action have a separate bordered box; unrelated VMs retain their own GPU summary. Selected-VM technical details occupy a separate box only for a recorded recovery/check problem, observed configuration difference, unsupported/missing VM, unreadable saved intent or VM-specific discovery issue. The complete non-hardware migration gate passed on 16 October 2026; its scope is recorded in [security](SECURITY.md#operation-recovery). Installed visual and multi-VM validation remain pending.

| State | Meaning | Does not establish |
| --- | --- | --- |
| Observed inventory | Last read VM/GPU/provider state | Saved intent or verified rendering |
| Saved intent | Valid production TOML committed for one VM | Current attachment or operation authority |
| Draft | In-memory requested changes | Enrollment, publication, or effects |
| Enrollment | Protected operator and exact VM/GPU authority | Desired enablement or guest health |
| Plan | Reviewed proposed actions from current inputs | Permission to reuse stale inputs or proof of completion |
| Journal / recovery receipt | Durable ownership and operation progress | Success merely because the frontend exited |
| Verification result | Checked guest device/rendering outcome for a recorded context | Permanent health, concurrent sharing, or resource isolation |

Stable VM GUIDs and exact GPU interfaces identify targets. Display names are presentation only. Sharing means several VM targets can reference one GPU; each VM has one selected GPU. The current global operation lock serializes protected operations; concurrent guest workloads do not require concurrent mutation workers.

## Operation flow

1. Discovery provides inventory and protected authority/managed state. The frontend reads committed intent separately and preserves drafts where appropriate.
2. A missing installation/pair prepares package/enrollment facts internally. The same foreground request performs permission setup, then verifies fresh authority/readback before continuing to GPU planning for the unchanged VM/GPU/draft. Permission setup itself does not apply GPU intent.
3. The selected foreground action asks the shared planner for exact selected-target actions and required downtime/credentials; no review dialog or second confirmation is displayed. The GUI uses a labelled preliminary review for ordinary changes with completed, non-pending setup history: host facts are fresh, but the payload digest is historical. Setup, adverse/missing history, repair and full reviews authenticate/hash current files. Read-only preparation can be cancelled; the read-only task finishes in the background and its late result is discarded. Background admission stays held until that task ends. Cancelling opens a modal waiting dialog that closes automatically when admission is released; the abandoned result cannot continue into execution. New operations remain disabled while waiting. The startup splash names each pending read before it starts, including protected inventory and recovery-record inspection; it does not automatically repair or replay unfinished operations. CLI full plans and Verify reviews retain current payload authentication.
4. Successful, still-current preparation continues directly into execution. Selecting the foreground action approves its required power transitions. The controller submits the prepared operation to a fixed elevated worker. The worker authenticates the session, acquires the lock, validates current enrollment/revisions, and recomputes approved facts using a freshly authenticated payload before admission or effects. Only the preliminary presentation marker is excluded from the exact plan comparison; payload, journal, host facts and effect scope must match. A changed payload/action set stops Apply before effects and makes the GUI's next preparation full; it cannot silently add guest setup or power work. Final independent payload authentication/readback still precedes publication.
5. Durable admission precedes effects. The shared workflow uses native host adapters and the guest bridge, then independently reads effective state. Initial setup includes graphics verification and confirmed final shutdown under APP-004. Ordinary enabled changes still repeat graphics checks until APP-006 separates them.
6. Successful effects and configuration publication remain separate phases. Publication failure leaves a bound save-only path; uncertainty leaves an explicit reconciliation path.
7. The frontend receives bounded progress/outcome information and refreshes independent state. A missing terminal message does not authorize replay.

## UI and platform constraints

Blocking discovery, payload work, and effects belong off the Slint event thread. UI updates return through event-loop callbacks; preserve stable selection, drafts, and editor focus when updating models. Installed status polling does inventory reads only. First-install elevation is not a timer side effect.

Rust is the product implementation. PowerShell Direct remains the current guest transport bridge; replacing it requires its own scoped work. The fixed transfer stream now uses a Rust-owned 4 MiB chunk limit injected into the bridge and shared with acknowledgement validation. Partial chunks send only the bytes read. Ordering, exact totals, deadlines and independent preparation verification remain separate from transfer acknowledgements. APP-013 runtime throughput and process-memory acceptance are pending. The deleted laboratory/reset tooling is not a product dependency. Non-Windows code paths do not establish Hyper-V support.

Verify diagnostics distinguish a guest device's observed nonzero Configuration Manager status from unavailable, denied, malformed or timed-out health queries. Native codes and device status are typed facts; adapter prose remains redacted. If verification and graceful power restoration both fail, frontends retain both safe diagnostic outcomes. These diagnostic facts do not authorize recovery retirement or establish current hardware health from historical success.
