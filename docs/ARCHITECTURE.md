# Architecture

This page owns component and data-flow boundaries. The [roadmap](roadmap.md) and [backlog](backlog.md) record current delivery status; [security](SECURITY.md) owns trust/recovery rules; [configuration](CONFIGURATION.md) owns formats and persistence.

The default application is `hyper-gpu-support.exe`. Setup currently expects that executable plus `hyper-gpu-runner.exe`, `hyper-gpu-guest.exe`, and `d3d11-probe.exe` in the same package directory. Internal setup/worker modes reuse the application executable; they are fixed protocol entrypoints, not general command execution. The installed runner is separate from the initiating user frontend.

The worker separates protocol/process authentication, client/server transport, locked dispatch, prepared execution, publication and recovery under [its module root](../src/worker/mod.rs). The [runner](../src/worker/runner/mod.rs) owns installed policy, scheduling, authenticated IPC, protected storage/audit and the native backend. The [live controller](../src/gui/live/mod.rs) coordinates foreground tasks and event-loop delivery; [live state](../src/gui/live_state/mod.rs) separates inventory, drafts, saved intent and observed recovery. Prepared plans and domain-specific requests are captured by their callbacks rather than copied into GUI state. Only event-loop callbacks update Slint models.

The GUI keeps a VM-bound [result notice](../src/gui/result_notice.rs) during a completion status retry. It contains presentation text only; no reviewed effect authority is retained. Refresh invalidates effect reviews before restoring a result's continuation. Closing or starting a new review drops the notice.

An explicit recovery action checks the recorded outcome for its bound VM. An `Admitted` receipt selects credential-free, record-only reconciliation; later records use the existing worker recovery path and retain uncertain outcomes. **Delete profile** starts separately from its foreground action, including during recovery or while the VM is running. It discards only the selected profile and interrupted-operation records without invoking Hyper-V or guest adapters; fixed file names, exact revisions, the common lock and resumable deletion progress preserve other profiles. A recovery dialog binds deletion to its named VM even when another VM was previously selected. There is no review confirmation or power checkbox. Worker admission, readback and uncertainty retention remain authoritative.

The fixed guest executable streams bounded `HGPREPARATION` phase labels at actual copied-file check, installation, installed-file check, current guest-file/receipt check and graphics boundaries. The authenticated transport relays those fixed events separately from the final JSON reply. The host [transfer monitor](../src/guest_transfer.rs) validates operation-specific ordering, bounds the phase queue and requires all expected phase boundaries for a successful worker reply. Coalesced byte acknowledgements remain independent. Phase delivery cannot certify success; worker exit, receipt/file readback, graphics and workflow lifecycle/publication checks remain authoritative.

Windows-version checking is deferred: setup provides an advisory warning, with no version probe, allowlist or version-based refusal. OS metadata remains display-only. The authenticated guest transport, signed payload, protected workflow and recovery boundaries remain required. See [security](SECURITY.md#guest-os-eligibility-before-installation).

Read-only preparation can be abandoned without publishing its late result or error. Its background read keeps foreground admission and the visible updating state until it finishes; drafts remain editable. Enabled Configure and Verify authenticate the current payload during each prepared invocation, retaining that backend and its authenticated files until the token is consumed. Disable remains payload-free. Historical preparation evidence determines required work but cannot replace current authentication. Reopening abandoned preparation does not cache authority or permit replay.

Every in-app modal uses the [shared dialog frame](../src/gui/ui/dialog-frame.slint): a centred neutral surface, common dimensions/padding/heading treatment, scrollable content and fixed footer. [Operation content](../src/gui/ui/install-dialog.slint) and [choices, notices and help](../src/gui/ui/dialogs.slint) share the [dialog footer](../src/gui/ui/dialog-footer.slint), which owns action choices, enabled/Close/Cancel rules, keyboard reveal and horizontal scrolling, plus the expandable, selectable and copyable [dialog log](../src/gui/ui/technical-output.slint). Task-specific content stays in the two dialog families. More Actions retains its vertical choices. The [display-only header controller](../src/gui/dialog_presentation.rs) selects phase labels from typed operation identity, independently of translated titles. Installation, permission checks/updates/reconciliation, plan building, Apply, Verify, recovery, saving, deletion and reads remain distinct. Readback appears only when it actually starts; terminal failures truncate future phases. Generic notices/help/choices clear previous phases. Apply keeps a fixed planned milestone order, stable completed ticks, sticky failures and the full repeated-event log; completion requires the terminal result and saved-state readback.

Successful fresh preparation continues directly into execution when the worker is available. Cancelled, failed or stale preparation cannot enter that continuation. Exact target/revision/package binding and worker admission remain. The foreground action authorizes its required power transitions, which appear as facts on the progress screen. Recovery starts only from an explicit recovery action, never from refresh or result publication. Native Windows authentication/UAC prompts remain. Action captions describe the operation they start.

Worker progress identifies VM readback, selected GPU/driver reads and signed-file authentication, including nested reads during admission and final checks. The headline returns to a still-running parent when a nested read ends; when no stage is active it waits for the final reply rather than showing a completed stage as the current work. Ordered event history and stage outcomes remain separate from final readback and publication. These source changes establish no measured performance guarantee.

## GUI task ownership

The GUI presents shared core facts and requests operations through existing callbacks. It does not own a second workflow engine.

| User task | Owner and shared mechanism |
| --- | --- |
| Select and inspect a VM | Observation model and selected-VM presentation; display metadata grants no authority |
| Edit desired resources | One draft, existing ResourceEditor/TextField controls and allocation rules; editing has no effects |
| Choose an operation | SelectedActions and existing Rust dispatch; More Actions keeps its intentional vertical choices |
| Acknowledge fresh preparation | Pure target/selection/revision/eligibility validation of the callback's captured plan; the worker retains its consumed admission token |
| Follow work and inspect a result | InstallDialog for operations, OperationDialog for notices/choices; shared frame, footer and copyable log |
| Complete or retry status | Common completion merge preserves terminal results and newer drafts; failed readback remains unknown |

Apply/Verify, enrollment, profile deletion and partial removal do not retain duplicate GUI approval stores. Their concrete checked domain requests pass directly from preparation into the existing operation callback; cancellation and stale-delivery suppression stay in the common background coordinator. Protected authority, package, revision and recovery records remain in their domain owners. During execution the interface shows target context, stage rows, progress and the technical log; its body is reserved for the terminal message. Removed frontend summary builders populated a hidden running body and repeated core plan facts. The core plan, exact allocation/power facts and technical log remain authoritative for presentation.

## Workflow module family

[Workflow root](../src/workflow.rs) retains the shared `Backend` trait and `OperationResult`, with private consumed admission tokens for production execution. Direct/reviewed-plan execution helpers are compiled only for isolated tests; the production worker uses prepared execution. Its private children own the operation stages:

| Module | Responsibility |
| --- | --- |
| [Journal](../src/workflow/journal.rs) | Durable state, setup eligibility, check persistence/readback and historical success timestamps |
| [Planning](../src/workflow/planning.rs) | Read-only decision gathering, reviewed effects and per-setting restoration calculation |
| [Apply](../src/workflow/apply.rs) | Consumed admission and guarded execution of the shared Configure steps |
| [Configure steps](../src/workflow/steps.rs) | One worker-owned typed sequence for preview and execution, including journal boundaries, exact category/settings writes and final power restoration |
| [Verification](../src/workflow/verification.rs) | Explicit Verify admission, current payload checks and operation-specific restoration guards |
| [Reconciliation](../src/workflow/reconciliation.rs) | Independently prove achieved outcomes and recorded lifecycle without replaying Apply |
| [Guest checks](../src/workflow/guest_check.rs) | Shared check classification, restored-negative evidence and graceful power restoration/readback |

Enabled Apply writes compatibility settings only when admitted initial settings differ from the reviewed target. Matching settings still acquire/retain the recorded ownership baseline, and final independent readback remains mandatory.

Operation modules depend on the shared contracts/helpers; Verify and reconciliation do not depend on each other's execution. Admission-token fields remain private to their operation modules; planning internals and shared primitives are visible only within the workflow family. The worker still owns authority, authentication, locks, protected receipts, publication and audit. Backend adapters and transport remain outside this family.

Focused tests live inline with their owning module. [Shared doubles/fixtures](../src/workflow/test_support.rs) and [cross-operation scenarios](../src/workflow/tests.rs) are compiled only under `#[cfg(test)]`. Current automated checkpoints and exclusions are recorded in [engineering](ENGINEERING.md#optimization-validation-checkpoint).

## Protected read pipeline

[Operational fact views](../src/model/operational.rs) compare VM identity, power, assignment, settings and allocations, plus GPU identity, driver and provider capabilities. Optional names, physical/display capacity and OS icons are excluded. Unknown or unavailable capabilities never become positive support. Reviewed intent, payloads, journals and revisions retain their existing binding.

[Read sessions](../src/windows_hyperv/reads.rs) reuse connections for one operation, with no mutable-object cache. [Batched inventory](../src/windows_hyperv/inventory.rs) joins realised settings to adapters through exact local provider object aliases and setting-data component associations. Ambiguous, duplicate or missing GPU relationships fail closed with attribution; failed relationship classes can fall back to independent per-VM inspection on the same connection. Effects still fetch fresh native objects and retain their existing guards.

[Observation bundles](../src/observation.rs) carry mode, selected identity, authority revision, complete saved-store revision, current enrollment, managed records, recovery and readiness from one common-lock read. Full Refresh fetches optional DXGI/KVP/name metadata; Poll re-reads topology and operational facts, retaining display metadata only for surviving VM IDs and exact GPU interface/PCI/driver matches. Missing identities disappear; unknown capabilities are never filled from old observations. Full Refresh replaces display observations rather than treating old metadata as current.

[Read control](../src/read_context.rs) propagates cancellation and a whole-read budget through native/provider, file/hash and pipe waits. [GUI coordination](../src/gui/live/polling.rs) gives foreground work priority, cancels an existing poll and waits for backend release before dispatch. Poll IDs and generations suppress obsolete delivery without claiming foreground busy/progress. Cancellation closes the read pipe; disconnect cancels server reads. Admission remains held until the exact scheduled runner instance confirms release, including failed/cancelled reads. Effects are tracked separately and are never cancelled by these read controls.

Completion gathers selected VM/GPU facts, saved intent, recovery and authority before releasing foreground admission. The existing protected `Bundle` is the single completion input; no wrapper duplicates its saved/recovery fields or permits completion without an observation. Its display-merge method validates the bundle before state publication. The GUI merges only this selected observation, preserves drafts/revision conflicts and the terminal result, and marks unrelated inventory historical until a subsequent poll or explicit Refresh. Failed/missing selected readback remains unknown and blocks new review; it never resurrects the previous row or selects another VM. Configuration publication still has independent durable readback, and recovery/enrollment continuation retains its existing authority checks. Readiness is presentation data, never execution permission. Recorded automated/install evidence is in the [checkpoint](ENGINEERING.md#optimization-validation-checkpoint); installed/live acceptance remains pending.

Exact journal, enrollment, operation-receipt and provider-completion comparisons use typed equality, including every field previously compared through JSON. Operational VM/GPU views retain their narrower presentation-independent comparison. Serialization remains necessary for wire/storage formats, revision hashes and normalized plan comparisons. VM GUID grammar belongs to `model::valid_vm_id`; individual stores/protocols still enforce canonical lowercase or normalize accepted uppercase input. These implementation changes require no persistent-format migration; see the [review](OPERATION_COMPLEXITY_REVIEW.md).

## Prepared worker execution

[Worker preparation](../src/worker/preparation.rs) implements a single process-bound preparation/approval exchange for Apply and Verify. The initial intent binds exact target/action and saved revision. Under the common lock, the shared workflow authenticates the payload once and returns the fresh plan while retaining its backend and private consumed admission token. The client checks the same selection/draft/revision on the event loop, publishes the authenticated checklist and obtains required credentials locally. A schema/session/review-revision acknowledgement approves only that exact plan; timeouts, disconnect, mismatched scope or credential rejection cannot execute it. The audit binds the prepared review before acknowledgement.

[Payload discovery](../src/payload.rs) opens all source files before hashing, and the [native backend](../src/worker/runner/backend.rs) retains handles that deny write/delete sharing across approval and execution. A fresh metadata/inventory guard detects changed driver/package/catalog membership before effects without rehashing the complete payload. No persistent cache is used. Every production native adapter is created through `NativeBackend::new`; read sessions, manifests, held files and storage paths are private to that adapter. The [shared Apply/Verify handler](../src/worker/operations.rs) consumes the token in that same backend. One receipt builder binds the exact prepared revision, original observations and operation-specific final power/settings/publication scope. One execution path persists `Admitted`, marks `EffectsStarted` before effects, independently confirms VM/GPU/current payload, and persists `Verified`. Only Apply then enters publication; Verify never publishes GPU intent. A failed write, effect, final check or progress delivery leaves its last durable receipt for explicit recovery. Recovery, save-only, import and enrollment admission remain separate.

The GUI keeps foreground admission for preparation, credentials, effects and completion; no second Apply/review dialog is introduced. Cancellation abandons read-only preparation, drains pending pipe IO and closes the connection, then waits for exact launched-process exit. Effect approval disables cancellation. Task rows append in actual first-start order and retain their model identity. Repeated executions get distinct rows; a new plan does not rebuild the checklist. Task timings and green tick icons are omitted. The grey context box contains only the bold VM, GPU and selected VRAM values. Technical Details preserves a reader's scroll position and follows appended output only at the bottom. Ordinary CLI changes, setup and Verify now share prepared worker execution. Explicit CLI `plan` remains full read-only authentication; its output grants no authority. Unused `PreliminaryPlan`, `ReinstallPlan` and `VerifyPlan` runner reads are removed. Reinstall and Verify obtain their plans through the same prepared worker session that executes them. Retired direct reviewed-plan Apply/Verify variants are absent from the wire command enum and rejected during bounded request decoding, before dispatch/admission/audit writes. The client validates terminal Apply/Verify replies against the retained authenticated `PreparedReview`, without constructing another command. The latest source validation is recorded in [engineering](ENGINEERING.md#worker-lifecycle-checkpoint); installed interaction and VM/GPU/guest acceptance remain pending.

Windows-version checking is deferred. Preparation uses its actual required boot without a separate identification cycle. Attached cases retain explicit shutdown/detachment. Compatibility warnings cannot block installation. A per-category allocation write set skips matching requests on retained adapters and includes every specified request after recreation; drift guards and final requested-value readback remain mandatory.

`Complete` is a session-bound terminal outcome; exact process exit proves release, not acknowledgement for guest/staging cleanup. Staging retention uses its own durable completion/readback criteria and preserves unresolved evidence.

## State separation

Startup displays the application name, a temporary monogram icon, the current read stage and the shared progress indicator while background observation completes. Installed reads use the protected bundle; first-install discovery retains its separate local inventory/configuration reads. Progress counts completed reads, not estimated time. Success opens the dashboard; failure retains one actionable summary with expandable redacted Technical Details and a normal-sized dashboard continuation button. The dashboard retains the failure for Inspect diagnostics even without a first inventory or selected VM; Refresh retries the same protected read and successful publication replaces VM/GPU models and clears the load failure. Empty-list guidance does not duplicate an active inventory notice. Original failures are classified before summary rendering so native codes are not lost through repeated redaction. No artificial delay is used. Installed startup/Refresh/diagnostics acceptance remains pending.

VM OS icons use optional host KVP `OSName` metadata, never the VM's display name or guest access. Direct XML element reads avoid XPath/type-spelling dependencies; CIM class/property identifiers are matched without case sensitivity; malformed unrelated entries do not suppress a valid OS entry. Missing, conflicting or unrecognised OS metadata uses the generic icon. Inventory refresh updates the existing row model, including OS changes and loss of detection. A single image binding selects bundled Windows, Tux or computer SVG assets; a neutral light plate keeps their colours visible in both themes.

The dashboard's outer viewport owns horizontal scrolling only; the VM list and details own vertical scrolling within the available height. The details scroll extent follows a trailing layout marker rather than relying on the preferred-height report of conditional nested layouts, including expanded allocation, wrapped text and diagnostics. Diagnostics reserve a usable text viewport, scroll offsets clamp after resize/collapse, and actions stay outside the scroll viewport. Operation dialogs share theme-specific neutral surfaces so standard Fluent control fills and states remain distinct. Installed visual and live VM acceptance remain pending.

VM effect recovery admission and presentation match stable VM IDs. Operation and provider receipts are retained separately for each VM, and the existing common lock still serializes operations. Another VM's held receipt does not block editing, reviewing or applying an enrolled VM's GPU changes; shared authority/import uncertainty and records whose scope cannot be established remain global blockers. The recovery warning and Inspect recovery action have a separate bordered box; unrelated VMs retain their own GPU summary. Selected-VM technical details occupy a separate box only for a recorded recovery/check problem, observed configuration difference, unsupported/missing VM, unreadable saved intent or VM-specific discovery issue.

| State | Meaning | Does not establish |
| --- | --- | --- |
| Observed inventory | Last read VM/GPU/provider state | Saved intent or verified rendering |
| Saved intent | Valid production TOML committed for one VM | Current attachment or operation authority |
| Draft | In-memory requested changes | Enrollment, publication, or effects |
| Enrollment | Protected operator and exact VM/GPU authority | Desired enablement or guest health |
| Plan | Reviewed proposed actions from current inputs | Permission to reuse stale inputs or proof of completion |
| Journal / recovery receipt | Durable ownership and operation progress | Success merely because the frontend exited |
| Verification result | Checked guest device/rendering outcome for a recorded context | Permanent health, concurrent sharing, or resource isolation |

Stable VM GUIDs and exact GPU interfaces identify targets. Display names are presentation only. Sharing means several VM targets can reference one GPU; each VM has one selected GPU. The current global operation lock serializes protected operations; concurrent guest workloads do not require concurrent mutation workers.

## Operation flow

1. Protected observation provides inventory, authority, managed state and committed intent together. First-install discovery retains separate local reads. The frontend preserves drafts where appropriate.
2. A missing installation/pair prepares package/enrollment facts internally. The same foreground request performs permission setup, then verifies fresh authority/readback before continuing to GPU planning for the unchanged VM/GPU/draft. Permission setup itself does not apply GPU intent.
3. The selected foreground action asks the locked worker to prepare exact actions and required downtime/credentials; no review dialog or second confirmation is displayed. GUI preparation authenticates once in that same worker session. Ordinary CLI effects use the same prepared session as the GUI; explicit CLI `plan` remains a full read-only authentication. Read-only preparation can be cancelled, keeps the draft and discards late approval. The modal cancellation dialog remains until exact backend release; new actions stay blocked. Startup names its pending reads and never automatically repairs/replays unfinished operations.
4. Successful, still-current preparation continues directly into execution. Selecting the foreground action approves its required power transitions. Prepared execution acknowledges the exact authenticated scope and consumes only the in-process token/manifest retained under the lock. Direct reviewed-plan worker submissions are rejected before protected admission/audit writes. The removed `OrdinaryPlan` request is no longer a runner operation; old clients must obtain matching binaries. Payload/action drift cannot silently add guest setup or power work. Final independent full payload authentication/readback still precedes publication.
5. Durable admission precedes effects. The shared workflow uses native host adapters and the guest bridge, then independently reads effective state. Initial setup includes graphics verification and confirmed final shutdown. Ordinary changes with completed setup evidence perform no guest preparation/graphics work; recreated adapters receive all specified categories and retained adapters only differing categories.
6. Successful effects and configuration publication remain separate phases. Publication failure leaves a bound save-only path; uncertainty leaves an explicit reconciliation path.
7. The frontend receives bounded progress/outcome information and refreshes independent state. A missing terminal message does not authorize replay.

## UI and platform constraints

The setup affordance and setup/removal operation title follow fresh host attachment, independently of enrollment, saved intent and retained driver preparation. A successful Remove GPU Support operation detaches host support and releases compatibility ownership; retained preparation/graphics receipts are historical and may still permit validated driver reuse when re-enabling. Unknown/historical observations do not establish removal. Dialog headers omit number badges when there is only one phase; informational `i` badges are not rendered. App text editors, including numeric/raw allocation inputs and diagnostic logs, use white backgrounds with black text in both themes. The shared editable field retains keyboard editing, clipboard/context-menu actions and accessibility value/selection handling.

Blocking discovery, payload work, and effects belong off the Slint event thread. UI updates return through event-loop callbacks; preserve stable selection, drafts, and editor focus when updating models. Installed status polling does inventory reads only. First-install elevation is not a timer side effect.

Rust is the product implementation. PowerShell Direct remains the current guest transport bridge; replacing it requires its own scoped work. The fixed transfer stream uses the Rust-owned [chunk limit](../src/guest_transfer.rs) injected into the bridge and shared with acknowledgement validation. Partial chunks send only the bytes read. Ordering, exact totals, deadlines and independent preparation verification remain separate from transfer acknowledgements. Runtime throughput and process-memory acceptance remain pending. Non-Windows code paths do not establish Hyper-V support.

Verify diagnostics distinguish a guest device's observed nonzero Configuration Manager status from unavailable, denied, malformed or timed-out health queries. Native codes and device status are typed facts; adapter prose remains redacted. If verification and graceful power restoration both fail, frontends retain both safe diagnostic outcomes. These diagnostic facts do not authorize recovery retirement or establish current hardware health from historical success.

Configure, save-only, Verify and workflow reconciliation share the event-loop completion owner in [state access](../src/gui/live/state_access.rs). It merges the captured terminal result and independent readback once, then presents current state. Publication and observation remain distinct; newer same-VM drafts survive completion, and readback failure retains known applied/published intent. Other record-management flows retain their own domain handlers pending the remaining simplification work. The [source checkpoint](ENGINEERING.md#core-simplification-checkpoint) passed its non-hardware gate; installed-GUI acceptance remains pending.
