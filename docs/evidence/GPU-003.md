# GPU-003 M1 baseline procedure and authorization scopes

## Status and gate

This document closes the M0 planning gate only. It executes no setup and grants
no authorization. The host currently has a pending file-rename reboot marker and
host Secure Boot remains unreadable to the normal token. No M1 mutation may begin
until the reason is explained and the owner explicitly approves an ordinary host
reboot immediately before it occurs, the marker clears, and a bounded administrator
read verifies Secure Boot and refreshes HV-001/CORE-001 inventory. The AI must not
schedule that reboot or infer permission from administrator/test-runner access.

The host target is Windows 11 Pro 25H2 build `26200.9457`, x64, with one NVIDIA
GeForce RTX 5060 (`VEN_10DE&DEV_2D05&SUBSYS_8A151043&REV_A1`) and driver 616.92
package `32.0.16.1692`. The native guest target is Windows 11 Pro 25H2 x64 updated
to the same `26200.9457` build before sealing. That guest version is a target, not
an observed result; mismatch stops sealing rather than being silently accepted.

the primary guest transport; no experiment requires guest networking.

For the native child, resolve the VM object from the enrolled VM GUID, verify its
fixed name and identity tuple, and add one adapter only while it is `Off` using
`Add-VMGpuPartitionAdapter -VM $verifiedEnrolledVm -InstancePath
<exact-interface>`. Do not change the host partition count and do not guess resource
units. Initial resource parameters are omitted so the provider's effective defaults
can be read back and recorded; GPU-010 owns measured resource tuning. A different
interface, an existing unexpected adapter or more than one assignment aborts.

## Parent seal and immutable checks

Before the first child and before every reset, the runner requires all of these:

- final parent is a single standalone VHDX: `Get-VHD` reports no `ParentPath`,
  not attached, correct 96-GiB virtual capacity and expected disk identifier;
- recorded SHA-256, length, NTFS file ID, volume serial, guest edition/build,
  Sysprep state and security settings match;
- backup has the same SHA-256 and remains outside the runner's writable allowlist;
- parent and containing directory are owned by Administrators/SYSTEM, ordinary
  users and the runner have read-only access, and neither can replace/delete the
  parent through parent-directory rights;
- file is read-only, no VM references it as a writable OS disk, no checkpoint/
  `.avhdx` chain exists, and no child other than the enrolled slot references it;
  and
- the runner opens the parent read-only and rejects any operation whose resolved
  target equals or lies under the golden directory except the fixed read needed
  by `New-VHD -Differencing`.

A mismatch does not trigger automatic repair, merge, move, permission takeover or
backup restore. Stop and return the observed identities for owner review.

## Ordered baseline procedure

1. **Stabilize host.** Explain the need and wait for explicit owner permission,
   then perform the single approved normal host reboot without scheduling a later
   restart. Confirm no pending reboot/servicing, confirm host Secure Boot, rerun
   exact inventory and require the GPU/package identities above.
2. **Build inputs without hardware mutation.** Build/sign nothing privileged.
   Acquire the pinned AppSandbox artifact/notices and complete CORE-020's GPU-008
   probes in a disposable build environment. Record all artifact hashes. A CUDA toolkit may
   build the sample but must not install/change a display driver.
3. **Host controls.** Run D3D11, D3D12 and CUDA probes unelevated on the host with
   the GPU-008 identity/output/timeouts. All must pass before a guest comparison.
4. **Reference comparison.** After BLK-003 is cleared and under its own authorization,
   use AppSandbox 0.1.9 with `testMode=false` on a recoverable branch of the existing
   stopped `Win11` reference candidate. Transfer, launch and retrieve the exact same
   probes only through the verified AppSandbox OpenSSH loopback/internal-NAT path;
   pin the endpoint/key or use an owner-supplied ephemeral credential, verify guest
   identity and re-hash transferred inputs. Capture its generated HCS identity,
   actual RTX LUID and driver/runtime state. Do not repoint or edit
   `%ProgramData%\AppSandbox\vms.cfg` manually; if the supported SSH path is not
   approved/available, record the comparison blocked rather than improvising.
5. **Prepare/seal parent.** Execute the exact build VM workflow above; capture the
   final guest/build/security/ACL/VHD/hash evidence and backup. Never boot the
   sealed parent.
6. **Install bounded runner.** Install the reviewed executable/policy and vacant
   enrollment under the separately approved boundary below. Verify denials for
   wrong paths/GUIDs, parent writes and unlisted operations before first reset.
7. **Create slot.** `reset-slot` validates the parent, creates `child.vhdx` as a
   differencing disk, verifies its parent path/file identity, creates/configures
   the fresh VM and atomically enrolls its generated GUID.
8. **Specialize/reach guest.** Start without GPU, complete OOBE if required, pass
   the guest credential only through the ephemeral credential channel, prove
   PowerShell Direct and collect clean guest inventory. Shut down gracefully.
9. **Assign.** Revalidate host/parent/slot/GPU/driver/VM-off state under locks, add
   the exact GPU adapter, read it back through cmdlet and WMI, then start.
10. **Stage.** Through a typed staging operation and PowerShell Direct, copy the
    GPU-002 217-file package and required `nvcuda.dll` alias, validating every
    pre/post hash. No shim, registry, ICD, junction, ACL or ownership transform is
    part of the baseline. Reboot the guest normally.
11. **Validate.** Reinventory device health, staged package and cross-API LUID;
    run GPU-008 D3D11, D3D12 and CUDA in that order after the required host control.
    Preserve structured results even on failure. Presentation is not in the pass.
12. **Recover/repeat.** On uncertain staging, device failure, interruption or
    deliberate recreation test, gracefully stop, detach, remove only the enrolled
    VM and child, rotate enrollment through `reset-slot`, then repeat from step 8.
    Never merge a child or restore through a checkpoint.

## Abort thresholds and timeouts

Abort before mutation for any identity/hash/policy/parent/reboot mismatch, an
unenrolled or externally changed VM, another GPU assignment, unexpected reparse
point, active checkpoint/saved state, parent writable handle, or less than 200 GiB
free on `Z:` for parent preparation / 120 GiB before child reset. Abort start when
host available RAM is below 12 GiB. During staging/probes, stop further writes if
`Z:` free falls below 80 GiB or result/log caps are reached; preserve the child for
diagnosis or mark it unusable.

| Operation | Deadline | Timeout outcome |
|---|---:|---|
| native read query | 15 s, 64 KiB stdout/stderr each | unknown/timeout; no mutation |
| graceful guest shutdown | 120 s | retain running VM; no force-off/delete |
| start/device readiness | 180 s | diagnose then graceful shutdown; child may be marked unusable |
| reset/create/enroll | 300 s | reconcile audit/native state; never guess/delete an unenrolled target |
| fixed runtime staging | 600 s, 4 MiB diagnostic cap | mark child unusable; recreate |
| essential probe suite | GPU-008 individual limits; 90 s total | fail and retain logs |

Force-off is not a normal operation. If a disposable enrolled VM cannot shut down,
a separate one-time destructive authorization may permit turn-off and discard of
that exact GUID/child, acknowledging guest data loss; it never broadens to another
VM or the parent.

## Fixed privileged runner boundary

Planned installed state (none exists yet):

| Component | Administrator-owned target |
|---|---|
| Executable | `C:\Program Files\HyperGpuSupport\Runner\hyper-gpu-runner.exe` |
| Policy | `C:\ProgramData\HyperGpuSupport\Runner\policy-v1.json` |
| Enrollment | `C:\ProgramData\HyperGpuSupport\Runner\enrollment-v1.json` |
| Replay state/locks | `C:\ProgramData\HyperGpuSupport\Runner\state\` |
| Append-only audit | `C:\ProgramData\HyperGpuSupport\Runner\audit\events.jsonl` |
| Per-operation privileged result | `C:\ProgramData\HyperGpuSupport\Runner\results\<operation-id>.json` |
| Client boundary | authenticated local named pipe `\\.\pipe\HyperGpuSupport.Runner.v1`; fixed versioned request schema |
| On-demand launcher | Task Scheduler path `\HyperGpuSupport\Runner-v1`; no periodic trigger |

The policy pins all paths/identities above, the physical GPU, one slot, timeouts,
binary/probe/manifest hashes and operation schema. The executable, policy,
enrollment, task and audit are not writable by the interactive user/repository.
The client cannot send a shell command, PowerShell text, executable path, new root,
VM name/GUID enrollment, GPU path or arbitrary file manifest.

Allowed request kinds are only `inspect`, `reset-slot`, `start-slot`,
`shutdown-slot`, `assign-gpu`, `remove-gpu`, `stage-runtime-v1`,
`run-probe-v1` (fixed IDs/hashes) and `read-result`. `reset-slot` is the only
operation that creates/deletes a VM/child or rotates enrollment. Every mutation
uses slot+GUID+nonce+plan fingerprint, fixed-order slot/GPU locks, immediate state
revalidation and a structured audit/result. No HCS fallback, feature/driver/
network/security change, parent write, arbitrary process, repository binary or
credential logging is allowed.

CORE-005 must first prove whether a dedicated local principal restricted to
Hyper-V Administrators can perform each operation. The install plan prefers that
principal with interactive/network logon denied. Any operation requiring a broader
administrator/SYSTEM token must be individually justified and re-approved; the
fixed allowlist remains mandatory.

Installation approval must name the executable/policy hashes, exact files/task/
principal/group/ACL changes, roots and uninstall path. Revocation first stops new
requests, verifies or safely removes the enrolled adapter/VM under a final explicit
operation, disables/removes `\HyperGpuSupport\Runner-v1`, removes the dedicated
principal/group membership and installed executable/policy/enrollment/state, and
retains or exports the audit/results. Installing, updating, broadening or revoking
the runner is itself protected; none occurred in M0.

## Separate authorization scopes prepared for M1

These scopes are intentionally separate so approval for one does not authorize the
others:

1. **Host stabilization:** after an explanation and explicit owner permission
   immediately before the operation, one normal reboot of this host, then a
   separately scoped administrator read-only Secure Boot/pending-reboot/Hyper-V/GPU/VM
   inventory. Effect: active applications and the user session stop; no configuration
   change requested. The AI must not schedule the reboot or derive consent from
   elevation/runner access. Recovery: normal boot and rerun reads.
2. **Parent preparation:** create only `HyperGpuSupport-ParentBuild-v1` and the
   `Z:\HyperGpuSupport\staging\parent-build-v1` files from the pinned ISO, temporarily
   use Default Switch for Windows servicing, Sysprep/shutdown, unregister build VM,
   create/protect the exact final parent+backup. Recovery deletes only the staging
   VM/files after identity verification; never touches the existing AppSandbox or
   repository-local export.
3. **Runner installation:** exact targets/effects/revocation above after CORE-005
   produces reviewed hashes and minimum-rights evidence.
4. **Native slot experiment:** fixed runner operations only for the current enrolled
   GUID under `gpu-pv-slot-01`; recovery is detach plus child/VM discard/recreation.
5. **AppSandbox reference:** launch the pinned signed artifact and create/use a
   recoverable branch of the exact `Win11` reference only. Its VMMS certificate,
   fixed HCN cleanup/network recreation, HCS/guest/disk changes and branch recovery
   must be enumerated at approval time; it does not authorize native-slot changes.

## Reference, native and presentation distinction

The AppSandbox candidate is an HCS-managed user-owned VM whose current config uses
`Default GPU`, a `Z:\Vms\Win11\...` branch disk and AppSandbox agents/VDD/runtime
provisioning, but has no persisted SSH enablement and cannot use PowerShell Direct;
BLK-003 owns that M1 transport gap. It proves the comparison path only after an
authorized run records the actual RTX identity. The native target is a VMMS/Hyper-V registered disposable
VM with explicit GPU-P interface selection and the minimal unmodified GPU-002
runtime. Their management, provisioning and display stacks are expected to differ;
the GPU-008 offscreen binaries/inputs and correctness rules do not.

VMConnect may be used for native OOBE/basic access; AppSandbox's own display may be
used for its reference. RDP/Enhanced Session can be reported separately. A visible
desktop, VDD frame or remote session is never D3D/CUDA evidence and session-specific
presentation failure does not rewrite an offscreen workload result.
