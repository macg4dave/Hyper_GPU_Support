## Notices and provenance limitation

The release ZIP does **not** contain the upstream `LICENSE` or
`THIRD-PARTY-NOTICES.md`. Therefore it must never be retained or handed off
alone. The acquisition directory must also contain those two files read directly
from reviewed commit `6f3adb6a...`, without modification. The MIT grant covers
AppSandbox's own source; the notices identify separately licensed WebView2,
DevCon, WDF, Mesa and other bundled components. No NVIDIA display driver is
contained in this release ZIP; AppSandbox later reads the operator's installed
driver package.

The missing notices do not prevent a bounded local reference experiment when
the exact source notices are paired with the asset. They do prevent treating the
ZIP by itself as a project distribution artifact. REF-003 owns the release audit.

## Why the prebuilt path is selected

The selected archive requires no compiler, SDK, WDK, signing key or source build.
The full solution is deliberately excluded:

- host/core/agent projects target MSVC `v143` and Windows SDK `10.0`; their link
  dependencies include HCS-adjacent Windows libraries, SetupAPI, Configuration
  Manager, Virtual Disk, DXGI/D3D11 and WebView2;
- VDD uses `WindowsUserModeDriver10.0`; VAD and SHM use
  `WindowsKernelModeDriver10.0`, so a WDK is required for the full solution;
- the release script requires the publisher's EV YubiKey and a Microsoft driver
  attestation round-trip, then replaces development drivers with Microsoft-signed
  packages; and
- command-line builds intentionally skip one WDK package-verification step.

A local source build would therefore not reproduce the selected signed release
and could leave test-signed driver outputs. No build or packaging script was run.
The pinned source remains the review basis; the publisher-signed archive is the
runnable comparison artifact.

## Acquisition recipe

Run these as an ordinary user in a new, dedicated reference-artifact directory.
They acquire and inspect files only; they do not launch AppSandbox:

```powershell
$uri = 'https://github.com/jamesstringer90/appsandbox/releases/download/v0.1.9/AppSandbox-0.1.9-win-x64.zip'
Invoke-WebRequest -UseBasicParsing -Uri $uri -OutFile '.\AppSandbox-0.1.9-win-x64.zip'
Get-FileHash -Algorithm SHA256 '.\AppSandbox-0.1.9-win-x64.zip'
```

Require the exact SHA-256 above, reject rooted or parent-traversal entries, then
extract to a new empty directory. Validate every `.exe`, `.dll`, `.sys` and `.cat`
with `Get-AuthenticodeSignature`; validate each INF against its catalog with the
Windows SDK x64 `signtool verify /kp /c <catalog> <inf>`. Recompute the 45-file
tree digest. Materialize `LICENSE` and `THIRD-PARTY-NOTICES.md` from the pinned
Git object beside the extracted directory. Fail closed on any mismatch.

The audited temporary copy was removed after inspection. Neither the ZIP nor its
contents is tracked by this repository.

## Launch and mutation contract

Do not infer that an archive is safe to execute merely because it is signed.
`AppSandbox.exe` requests administrator elevation. `--headless` additionally
fails unless it has an elevated token and Virtual Machine Platform is enabled.
Static review shows that startup, before a new VM is requested, can:

- create/truncate `%ProgramData%\AppSandbox\headless.log`, create a bearer-token
  `host.json`, bind a loopback HTTP endpoint and load `vms.cfg`;
- create a 100-year, exportable machine-key VMMS certificate in
  `LocalMachine\My` when none with the VMMS OID exists, and grant
  `S-1-5-83-0` read access to its private key;
- delete the three fixed AppSandbox HCN network GUIDs as stale cleanup; and
- reconnect configured HCS VMs; normal cleanup terminates VMs it regards as
  running.

VM creation can create/delete HCS compute/network objects and VMGS/VMRS/VHDX
state, change ACLs, stage the host NVIDIA package, provision guest files and
drivers, modify guest registry/boot policy and install guest services. The GUI
can also offer to enable Virtual Machine Platform and reboot the host. These are
protected operations, not an artifact-acquisition step.

For the reference baseline, GPU-003 must name the exact AppSandbox VM/disk/network
targets and recovery path before seeking authorization. It must prohibit feature
enablement, host reboot, host boot-policy change, host driver installation,
signing-key access and test mode. Use `testMode=false`: the reviewed x64 Windows
HCS document applies Microsoft's Secure Boot template, while `testMode=true`
omits Secure Boot and writes guest `bcdedit /set testsigning on`. Even with
`testMode=false`, AppSandbox's unattended guest setup changes guest recovery/boot
policy; that behavior must remain confined to its reference VM and must never be
applied to the project's immutable parent.

No code path reviewed here disables host Secure Boot or host code integrity.
That is a static source conclusion, not a runtime assertion. GPU-004 must record
the actual host and guest Secure Boot/test-signing state before and after the
authorized reference run.

## Existing reference state found read-only

`C:\ProgramData\AppSandbox\vms.cfg` already describes a completed Windows VM
named `Win11`, GPU mode 1, using
`Z:\Vms\Win11\snapshots\branch_0da34e13-31c4-49f8-a898-ac19c40bd385.vhdx`.
The 91,440,021,504-byte VHDX and the configured 7,736,125,440-byte Windows ISO
exist on healthy NTFS volume `Z:`. The entry has no `TestMode=1`, but selects
`Default GPU`, not the project's explicit RTX interface. It is evidence of an
existing reference candidate only; it is not enrolled, opened, started, changed
or claimed disposable. GPU-003 must either scope this exact user-owned VM for a
read-only/controlled probe or specify a separately recoverable reference target.
Actual adapter identity must be checked in the guest before its results can be
compared with the project path.
