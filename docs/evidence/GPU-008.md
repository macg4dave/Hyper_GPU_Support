# GPU-008 reproducible probe kit

## Status and selection

This is a specification, not execution evidence. No probe was built or run for
this task. M1 must use the same pinned binaries, inputs and acceptance rules for
the host control, AppSandbox reference and native Hyper-V guest.

Existing small official samples were reviewed first. Microsoft's DirectXTK
simple-rendering guidance and D3D12 HelloTriangle demonstrate the required draw
paths, but they present to a window, allow environment/session differences and do
not read back or check the image. NVIDIA's `vectorAddDrv` already exercises
explicit device allocation, host/device transfers, kernel execution and CPU
comparison, so it is selected unchanged. The two Direct3D probes will be minimal
project-owned Rust probes, following the official triangle setup but deliberately
rendering offscreen with fully checked output. CORE-020 owns their standalone
implementation; CORE-003 later owns core invocation/report integration;
this task adds no application skeleton.

## Common execution and identity contract

Each probe is a console process with machine-readable JSON on stdout, diagnostic
text on stderr and one of these exit classes: `0=pass`, `2=wrong/unavailable
adapter`, `3=API/runtime unavailable`, `4=execution failure`, `5=incorrect
output`, `6=timeout/cancelled`, `7=malformed input/internal error`. CORE-020 may
refine the encoding but not collapse these meanings.

Before any workload:

1. inventory the guest adapter and record description, vendor/device identifiers,
   DXGI LUID, software flags, driver version and staged-package tree digest;
2. select the NVIDIA adapter explicitly; reject `DXGI_ADAPTER_FLAG*_SOFTWARE`,
   Microsoft Basic Render Driver, WARP and a default/enumeration fallback;
3. require the D3D11 and D3D12 device LUIDs to match each other and the inventoried
   guest NVIDIA adapter; and
4. obtain the CUDA device name, UUID, compute capability and LUID. Require
   `NVIDIA GeForce RTX 5060`, compute capability 12.0 and the same Windows adapter
   LUID. A missing/zero/uncomparable LUID is a failed identity check, not a pass.

The selected physical host identity remains
`VEN_10DE&DEV_2D05&SUBSYS_8A151043&REV_A1` / bus `00000000:01:00.0`; a virtual
guest bus address need not equal it. Correlation is through the explicitly
assigned GPU, staged package and cross-API LUID, with the host PCI identity
recorded alongside the result.

All essential probes are non-interactive and must not depend on RDP, VMConnect,
an indirect display driver, a swap chain or an attached monitor. Presentation is
reported separately. Transport is target-specific while binaries and correctness
rules remain identical:

- host controls run locally under the normal user token in the caller's recorded
  Windows session;
- the registered native child uses a persistent PowerShell Direct session addressed
  by the enrolled VM GUID, with ephemeral guest credentials and bounded copy/invoke/
  result retrieval; record the guest process session (normally service session 0);
- the HCS-managed AppSandbox reference is not addressable by PowerShell Direct.
  It may use only AppSandbox's supported OpenSSH path over its loopback proxy or
  host-only internal NAT, with a pinned endpoint/key or owner-supplied ephemeral
  credential, verified guest identity, bounded copy/exec/result retrieval and no
  external exposure. Its current persisted configuration does not enable SSH, so
  [BLK-003](../BACKLOG.md#blocker-register) must be cleared before a reference run.
  Do not edit `vms.cfg`, inject through the clipboard or extend the guest agent.

## D3D11 checked offscreen render

The Rust probe uses `windows` bindings and the selected `IDXGIAdapter` directly.
It calls `D3D11CreateDevice` with no driver-type fallback and requests feature
levels in order `12_1, 12_0, 11_1, 11_0`; success requires at least `11_0` and
records the negotiated value. The HLSL is compiled once with Windows SDK
`10.0.26100.0` as `vs_5_0` and `ps_5_0`; compiler version, source hash and bytecode
hash become artifact-manifest fields.

The workload creates a 256x256 `DXGI_FORMAT_R8G8B8A8_UNORM` render target, clears
it to cyan, then draws the standard oversized full-screen triangle with vertices
`(-1,-1)`, `(-1,3)`, `(3,-1)`. The pixel shader emits opaque magenta
`float4(1,0,1,1)`. It copies to a staging texture, maps it, removes row padding
and checks every RGBA byte. Expected canonical bytes are 65,536 repetitions of
`ff 00 ff ff`; their SHA-256 is
`00f88da6c22b46ab45bfc5fbc6659e601ebcefe324d52a3302e614d4a7fb3de4`.
Any non-magenta pixel, map/copy/device-removal error or different hash fails.

## D3D12 checked offscreen render

The Rust probe uses the same selected DXGI adapter and calls
`D3D12CreateDevice(adapter, D3D_FEATURE_LEVEL_11_0)`. It queries and records the
maximum supported feature level from `12_2, 12_1, 12_0, 11_1, 11_0`, plus the
highest shader model. The chosen pipeline requires Shader Model 6.0; the pinned
stable DXC compiles `vs_6_0` and `ps_6_0` with `-Ges -WX`. Success requires an
SM 6.0-capable hardware device and records both the requested minimum and actual
maximum rather than relabeling one as the other.

It uses the same dimensions, format, clear, vertices, pixel value and canonical
SHA-256 as D3D11. The command list transitions render target -> copy source,
copies into a readback buffer, signals a fence, waits with a bounded event and
checks every unpadded byte. A fence timeout, device removal, wrong state/copy,
non-magenta byte or different hash fails. No WARP fallback is compiled into the
probe.

## CUDA allocation/transfer/kernel check

Build only `cpp/0_Introduction/vectorAddDrv` from the pinned CUDA Samples commit
with CUDA Toolkit 13.4.1, CMake >=3.20, an x64 C++17 MSVC host compiler and:

```powershell
cmake -S . -B build -A x64 -DCMAKE_BUILD_TYPE=Release -DCMAKE_CUDA_ARCHITECTURES=120
cmake --build build --config Release --target vectorAddDrv
```

Record the actual CMake, MSVC, `nvcc --version`, source-tree, EXE and FATBIN
hashes. Verify the FATBIN with `cuobjdump` and require an `sm_120` image; do not
silently build only an older SASS target or rely on an unrecorded JIT target.
Retain the sample's BSD notice. No CUDA Toolkit or compiler is required in the
test guest: the resulting `vectorAddDrv.exe` and `vectorAdd_kernel64.fatbin` use
the staged `nvcuda.dll` driver path.

Run `vectorAddDrv.exe --device=0` with its fixed `N=50000`. The selected sample
performs three `cuMemAlloc` calls, two host-to-device copies, `cuLaunchKernel`, a
device-to-host copy and element-wise CPU comparison with tolerance `1e-7`, then
returns failure on the first mismatch. Require stdout `Result = PASS`, exit 0,
and the separately captured device/LUID/CC 12.0 identity. A load/enumeration-only
result, unified-memory-only sample, missing FATBIN or output text with nonzero
exit status does not pass.

## Run matrix, timing and interpretation

| Probe | Deterministic input/output | Expected duration | Hard process timeout | Pass condition |
|---|---|---:|---:|---|
| D3D11 offscreen | 256x256 full-screen magenta; exact hash above | <2 s | 15 s | hardware identity + FL >=11_0 + SM5 bytecode + exact bytes |
| D3D12 offscreen | same image/hash | <2 s | 15 s | same hardware LUID + SM >=6.0 + completed fence + exact bytes |
| CUDA `vectorAddDrv` | 50,000 floats; CPU comparison `1e-7` | <3 s | 30 s | RTX/CC12/LUID identity + allocation/copies/kernel + exit 0/PASS |

The essential suite has a 90-second overall deadline including inventory, with
individual process output capped at 1 MiB and cancellation followed by process
termination and device-state reconciliation. A timeout is `fail`, not `skip`.
First failure stops mutation/progression but retains logs. Probe failures are
classified independently as identity, runtime/load, device creation, execution/
device loss, timeout or incorrect output.

Run each exact binary/input first on the host as the positive control, then in
the AppSandbox reference, then in the native disposable child. Re-hash binaries
at the source and after each target transfer. The target-specific launch contracts
above must capture the same command, exit status, bounded stdout/stderr and result
files. Host control failure or an unresolved reference transport blocks comparison.
Run one warm-up that is
reported but not counted, then three measured correctness repetitions per API in
M1; all three must pass. GPU-012 owns longer endurance/pressure counts.

Each result records project/upstream revisions, UTC time, session type, host and
guest build/architecture, physical and guest adapter identities/LUIDs, driver and
staged tree, probe/toolchain hashes, feature/shader/compute levels, command, input,
duration, exit class, canonical output/hash and logs. Compilation success,
enumeration, a loaded DLL or plausible performance is never a workload pass.

## Acquisition and security boundaries

Sources and tools are downloaded only from the named upstreams, pinned by commit
or release plus hash, with their licenses/notices retained. Probe artifacts contain
no NVIDIA display driver, Windows DLL, credential or signing material. Toolkit or
SDK installation, if needed to build, is separate from guest runtime staging and
must not update the host display driver. Default/CI tests never invoke these
hardware probes or protected VM operations.
