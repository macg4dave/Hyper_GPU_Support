# GPU-002 selected driver and runtime manifest

## Scope and conclusion

This specification was derived on 2026-09-25 for the selected Windows 11 x64
host and NVIDIA RTX 5060. It inspects the installed NVIDIA package and pinned
AppSandbox 0.1.9 source; it does not copy, modify or distribute a driver.

The initial native experiment shall stage the complete, exact signed x64 NVIDIA
DriverStore package into the disposable guest's `HostDriverStore` mirror. It
shall not install the INF, rewrite a binary, import AppSandbox's provisioner or
shims, or enable optional API workarounds. This preserves the package dependency
closure while keeping Windows-owned guest components and NVIDIA-owned files
separate. Optional APIs and compatibility hooks are conditional experiments,
not baseline inputs.

## Required baseline manifest

`<package>` means `nv_dispi.inf_amd64_b20cc8aeaed64fc2`. Sources are resolved
from the GPU-correlated host package, never a hard-coded current directory.

| Owner | Source | Disposable-guest destination | Class | Operation |
|---|---|---|---|---|
| NVIDIA | Host DriverStore `FileRepository\<package>\**` | `%SystemRoot%\System32\HostDriverStore\FileRepository\<package>\**` | required | Copy the complete verified tree, preserving relative names and file bytes. No INF installation or binary transform. |
| NVIDIA | staged `nvcuda_loader64.dll` | `%SystemRoot%\System32\nvcuda.dll` | required for CUDA probe | Create a guest-local hard link when same-volume semantics permit; otherwise make a byte-identical copy and record which method was used. Never link back to the host. |
| Windows | clean guest OS GPU-P virtual device, kernel/runtime and DirectX components | existing guest locations | required | Use the guest's own installed Windows files. Do not copy host Windows binaries. |
| Project | probe kit selected by GPU-008 | versioned non-system test directory | required | Copy only separately licensed probe artifacts after hash validation. |

The whole NVIDIA package is required as an atomic versioned dependency closure,
not because every file is exercised by the essential probes. The essential path
uses the package's D3D user-mode components and CUDA loader/implementation. It
does not treat the directory copy as a normal PnP driver installation: the guest
continues to use its Windows-provided GPU-P device and redirects vendor user-mode
loads to the `HostDriverStore` mirror.

The observed host aliases support the rule above: System32 `nvcuda.dll` is a
hard link to package `nvcuda_loader64.dll`; System32 `nvapi64.dll`, `OpenCL.dll`
and `nvofapi64.dll` are hard links to their package equivalents. They are
observations, not blanket instructions to replace guest System32 files.

## Optional and deferred effects

The baseline has no registry write, ICD JSON rewrite, junction/reparse point,
ownership change, ACL broadening, System32 backup/replacement, shim, or modified
binary. Destination directories and files are created only inside the disposable
child. Existing unexpected destinations make the plan fail closed; the recovery
path is child discard/recreation, not takeover or deletion of unknown state.

Optional work may be proposed only after an independently recorded failure or an
optional probe requires it:

| Capability | Potential files/effect | Baseline disposition |
|---|---|---|
| OpenCL | guest `OpenCL.dll` alias plus staged `nvopencl64.dll` | optional; no alias initially |
| Vulkan | x64 ICD JSON copied to a project-owned location with `library_path` rewritten to the staged package; explicit registry registration may be needed | optional; retain original hash and transformed hash, do not modify the package copy |
| OpenGL | `nvoglv64.dll` and Windows OpenGL dispatch interaction | optional; no System32 replacement |
| NVAPI/NGX | `nvapi64.dll`, `_nvngx.dll`, possible NGX junction/reparse point | experimental; no junction or ACL/owner change |
| Optical Flow/OptiX/video | `nvofapi64.dll`, `nvoptix.dll`, codec components | experimental; stage only for a named probe |
| AppSandbox compatibility hooks | built shim/provisioner artifacts and System32 backups/replacements | excluded unless an essential failure is reproduced and a separately reviewed hook experiment is approved |

Any later transform must have an exact preimage hash, destination, postimage
hash, backup/restore rule, ACL/owner delta, reboot requirement and disposable
recovery test before execution. A `.asbak` naming convention alone is not a
recovery guarantee.

## Pinned-reference dependency closure

The inspected reference is AppSandbox 0.1.9 commit
`6f3adb6aafd4fc819d7715bdfacf52ac87df26a6`, preserved at
`refs/upstream-reviewed/appsandbox/0.1.9`.

- `src/backend_win/gpu_enum.c` resolves the selected adapter's DriverStore folder
  through SetupAPI, shares the whole folder and substitutes `DriverStore` with
  guest `HostDriverStore`. This supports the atomic package rule.
- `tools/agent/gl_vk_provision.c` can rewrite Vulkan ICD JSON through a temporary
  file and `.asbak`, replace/back up System32 OpenGL/CUDA/OpenCL/NVAPI files,
  grant file control, create NGX junctions and stage Optical Flow/OptiX. Those
  broad effects are deliberately not inherited by the native baseline.
- `cuda_opencl_adapter_hooks.c`, `nvapi_shim.c` and `opencl_shim.c` show that the
  reference's CUDA/OpenCL adapter-identity hooks are connected through its NVAPI
  wrapper. NVAPI is therefore a possible compute-hook dependency even when NGX
  or DLSS is not requested.

That last dependency matters only if an essential CUDA/OpenCL identity failure is
reproduced. The first CUDA run uses the unmodified NVIDIA path. A hook experiment
must then pin and inspect the reference build, exports, original DLL backups and
restore behavior under REF-002; it cannot silently promote the NVAPI shim into
the baseline.

## Drift, reboot and failure rules

Staging must stop before copying when any of these is true:

- the GPU-correlated package directory, INF version, 217-file extent, package-tree
  digest, catalog hash or signature differs;
- Windows or the NVIDIA driver changed after the inventory, an install is active,
  or Windows reports a pending reboot;
- the selected physical-GPU interface no longer correlates to this package;
- the guest already contains a mismatched package mirror, alias or optional
  transformation; or
- the immutable parent fingerprint, disposable child identity or runner-owned VM
  enrollment differs from GPU-003's reviewed plan.

After a stable host reboot or any Windows/driver update, rerun HV-001/GPU-002
inventory and generate a new manifest; never update this manifest in place while
an experiment is pending. After staging, cold-start or reboot the disposable
guest before probing and record the actual requirement. This is a conservative
procedure, not evidence that every file inherently requires a reboot. Any partial
copy or validation failure invalidates the child; recreate it from the unchanged
parent rather than attempting an in-place repair.

## License and distribution boundary

The installed `license.txt` is a collection of component/third-party notices,
not a standalone grant to redistribute this Windows driver package. NVIDIA's
current CUDA EULA states that it also applies to the NVIDIA Display Driver,
limits distribution to identified distributable portions and lists Linux—not
Windows—CUDA driver libraries in its distributable attachment. It also prohibits
copying or distribution except where expressly provided. See the official
[NVIDIA CUDA EULA](https://docs.nvidia.com/cuda/eula/) (updated 2026-01-26).

Accordingly, this project does not place NVIDIA driver files in Git, build
artifacts or releases and does not represent the installed Windows display-driver
package as redistributable. The later local experiment may stage files only from
the operator's own installed/licensed package into that operator's disposable
guest, with notices preserved. REF-003 must audit release contents and rights;
legal uncertainty stops distribution and should be resolved with NVIDIA. This is
an engineering boundary, not legal advice.

## Inspection record

Read-only inspection used DriverStore/INF and filesystem metadata, SHA-256,
Authenticode status, hard-link identity, and selected source files from the pinned
Git object. No setup script or upstream binary ran. No file was copied into a
guest, no registry/ACL/owner/junction changed, no NVIDIA binary was modified and
no driver artifact was added to the repository.
