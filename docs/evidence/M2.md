### Read-only Rust resource review

Review of the new product and independent native-boundary review found no unbounded
production spawn loop or substantial normal-path handle/COM leak. Saved snapshots
contained one product runner and one frontend when active; they cover selected
process names at particular times, not total host process growth or memory usage.

- `windows_hyperv::power` polls full `inspect` after a 200 ms sleep, reconnecting WMI
  and querying GPU state during slow transitions. A power-only poll followed by
  full final verification would reduce provider load.
- Every enabled `workflow::apply` discovers/hashes the complete payload;
  `NativeBackend::payload` also authenticates it, including unchanged reapply.
  Hashing streams through a 64 KiB buffer, but repeated reads/signature checks can
  add disk/CPU/security-provider pressure. This is not payload-sized Rust heap use.
- Child jobs enforce lifetime/cleanup, not memory/CPU/process-count ceilings.
  The fixed bridge can run for up to an hour without resource-pressure monitoring.
- A raw BSTR VARIANT in attachment arguments can leak if a later fallible argument
  fails before `invoke` takes ownership. It is small and reclaimed when the
  one-shot runner exits; it is not a credible explanation for host-wide exhaustion.
- The probe submits one triangle into two 256×256 textures, not a repeated stress
  loop. Hyper-V/GPU-driver work remains a possible host-level contributor even
  without a Rust heap/process leak; no causal claim is established.

No builds, tests or live effects were run for this review. At that point the recommendations
were unimplemented and M2 remained blocked. Do not bypass per-run integrity checks merely
to remove their cost. First reduce unnecessary polling and capture host commit,
available memory, process/handle counts and provider activity before reproduction.
